Domain 5

Hang & crash protection

Two independent layers for a hung guest or subprocess, one honest limit neither removes, a third failure mode — a hung rebuild — isolated from the UI and bounded, and a limit on how often a crashing app is restarted.

D5.1

Epoch interruption bounds a guest call with no cooperation from the guest

accepted

wasmtime's epoch interruption (Config::epoch_interruption, and a thread that advances the engine's epoch every 10 ms) traps a guest call that runs past its deadline, 500 ms, set before every call and before instantiating, which runs the component's start-up code. The trap is recovered from like any other (D5.3). It traps — even a bare loop {} with nothing in it, since the compiler (Cranelift) inserts the check at every loop backedge, not at some cooperative checkpoint the guest author has to call.

Alternatives considered
  • Fuel (Config::consume_fuel and a per-call budget) — what this entry left open beside epochs. Rejected: it counts instructions, where the contract (D5.5) is about time, and it costs a check on every instruction where an epoch is only checked at backedges and function entries.
  • Cooperative heartbeats from app code — rejected outright. A heartbeat only proves the thread emitting it is alive, not that a specific call will ever return (a heartbeat thread can run forever alongside a guest call that never finishes — the same shape as the fuel-exhaustion case this decision solves, but without a hard bound). It also requires instrumentation from a third-party app author that can't be assumed or enforced.
  • OS-level thread termination of a hung call — TerminateThread/pthread_cancel-class operations are documented as unsafe to rely on; they can leave process state (locks, heap) corrupted rather than cleanly recovered.
Reasoning

This is the property that decided D2.1. It's genuinely inherent to wasm's execution model (compiled backedge checks), not available to either native-dylib alternative without inventing an equivalent from scratch.

Consequences

Engine::default(), what the drafts used, has neither configured; it has to be set explicitly. 500 ms is far above any legitimate frame call, even in a debug build, and under the host's one-second reply timeout (D5.2), so a runaway call is caught inside the subprocess, which recovers, before the host gives the whole subprocess up. The store's initial deadline is 0: without one set before instantiating, the component traps in its own start-up code.

D5.2

A flat timeout on the subprocess round-trip is a second, independent layer

accepted

Host applies a timeout to "did the subprocess respond to this request," separate from and in addition to D5.1. The same ceiling applies to the child connecting to the IPC named pipe in the first place (D4.2), since waiting for that connection has no built-in timeout of its own: 5 s to connect, 1 s per request, and 60 s for Start, which compiles the component.

Reasoning

D5.1 only guards execution inside a wasm call. It says nothing about a hang in the subprocess's own harness code, or in wasmtime instantiation itself — failure modes that have nothing to do with the guest. This layer catches those. It's deliberately dumb (a flat ceiling, not a smarter heuristic) for the same reason D5.5 is: there's no reliable signal available from outside a process that distinguishes "still working" from "stuck," cooperative or not.

Consequences

A timeout marks the subprocess lost (D5.8). One second is generous for a frame call, but it bounds how long the host waits on a stuck subprocess before showing its notice.

D5.3

A trap must be caught at each call site and turned into "discard this generation," never propagated to main

accepted

A guest trap — a panic, or D5.1's deadline — means "this generation is bad," never "the host process exits." The subprocess drops the request and starts a new generation from the latest state: from the component before the last reload if the trap follows one, since the new code is the likely cause, else from a new instance of the same component. It answers Recovered with that generation's state.

Reasoning

The sandbox in D2.1/D5.1 prevents a trap from corrupting host memory or hanging — it does not, by itself, make recovery automatic. Every wasm draft built so far calls logic.on_tick.call(...)?/handle_event.call(...)?/build_view.call(...)? with the error-propagating ? operator, which unwinds straight out of the host loop. A trap today still exits the whole process — cleanly, via a normal error return, instead of via undefined behavior, but it still exits. wasm makes graceful recovery possible; this decision is what would make it actual.

Consequences

The previous component is kept until the next reload, so going back is one instantiation. A recovery counts toward D5.9's limit, so a generation that traps on every request doesn't loop forever.

D5.4

A failed module load keeps the previous generation running

accepted

If a rebuilt module fails to load — a build error, the D2.2 signature-mismatch case, or the D3.4 wire-schema mismatch — the currently-loaded generation keeps running untouched. There is no "no logic loaded" state reachable after the first successful start.

Reasoning

This is already how every wasm and dylib draft's reload logic works (build_and_load returning Ok(None)/Err leaves logic unassigned, so the previous binding stays in scope) — stated here explicitly because D5.3 depends on the same pattern existing for in-flight traps, not just failed reloads.

D5.5

No attempt is made to distinguish "slow but legitimate" from "hung" inside a frame call

accepted

Any on_tick/handle_event/build_view call that exceeds a short, fixed budget is treated as a bug, full stop — not diagnosed further, not given the benefit of the doubt.

Alternatives considered
  • Heartbeat-based liveness — already rejected in D5.1 for the same underlying reason.
  • CPU-usage sampling to distinguish "burning CPU productively" from "spinning uselessly" — doesn't actually resolve the ambiguity; both look identical from outside (100% CPU, no response). Useful only as a diagnostic ("spinning" vs "deadlocked, ~0% CPU"), never as the basis for the kill decision itself.
Reasoning

Telling apart a legitimately slow computation from a true infinite loop from outside the call is not reliably decidable in general. The way out is a contract, not a smarter detector: a TUI frame call has no legitimate reason to take more than a few milliseconds — it's producing a screen of text, not doing heavy computation — so any overrun is a contract violation by definition, whichever of D5.1/D5.2 catches it.

D5.6

The rebuild step runs on its own background thread, never inline in the render/event loop

accepted

A notify watcher on the app's src/ and manifest triggers a rebuild, which runs cargo build on a dedicated OS thread, its output going to the log. Only edits count — a file created, removed, renamed or written — and changes are batched until the sources stay quiet for 200 ms. The main host loop — rendering, input, ticking — is never blocked waiting on it, regardless of how long the build takes or whether it ever completes at all.

Alternatives considered
  • Run cargo build inline in the host loop — what every wasm/dylib draft does today. The whole TUI freezes for the entire build duration, and hangs outright if the build itself hangs.
Alternatives considered
  • Count every file-system event — rejected after it was tried: building reads every source, so the build's own reads triggered the next build, forever.
Reasoning

This is the exact pattern already proven elsewhere in this codebase, not a new technique: termoxide_event's input reading and the hot-lib-reloader draft's own rebuild watcher both already run on a background thread, decoupled from their main loop (D10.3). Applying the same pattern to the wasm/dylib hosts' rebuild step is what actually delivers on D1.1's promise of not losing the running app to an edit — the app stays up and responsive whether or not the rebuild ever finishes.

Consequences

This fixes the symptom — a frozen TUI — but not the underlying resource question. A cargo build child process that genuinely hangs is still running, stuck, forever, on that background thread; nothing here reaps it, bounds it, or tells anyone it happened. D5.7 does.

D5.7

A hung rebuild still needs its own kill timeout, and overlapping rebuilds need preventing

accepted

The background thread in D5.6 has a flat ceiling of its own, 10 minutes — minutes, not milliseconds, since a real build can legitimately take a long time — after which the stuck cargo build child is killed outright and the failure is surfaced to the shared log (Domain 6), rather than left silently running forever. There is one rebuild thread: a file save arriving while a rebuild is in flight makes one more build after it, never a second, overlapping build competing for the same target directory and lock.

Alternatives considered
  • Leave a hung build running indefinitely (the gap D5.6 leaves open by itself) — a stuck build becomes invisible rather than failing loudly: the app stays responsive, but the edit the user made simply never takes effect, with no signal anything is wrong.
Reasoning

Moving the wait off the main thread (D5.6) solves responsiveness, not resource accumulation or diagnosability. Without a kill timeout, a genuinely stuck build is silent forever instead of failing loudly; without a single-in-flight guard, repeated saves during that stuck build would spawn additional overlapping cargo build invocations, each competing for the same lock.

Consequences

The kill-then-report pattern is the same shape as D5.4 — a timed-out build should be treated identically to a failed one, not as a new case. D1.1 still refuses to state a reload-latency number: the timeout bounds a hung build, not a slow one.

D5.8

A subprocess that dies, hangs or breaks the protocol is killed and respawned in the background, never reconnected

accepted

Any IPC failure on a request — the pipe closing, a D5.2 timeout, a malformed message — or the child exiting marks that child as lost. The host kills it if it is still alive, reaps it, logs why, drops the in-flight call without retrying it, and spawns a replacement on a fresh pipe in the background, starting from the host's copy of the state (D3.3). The render loop keeps running meanwhile, on its last frame and still taking input, so the interruption lasts only as long as the respawn.

Alternatives considered
  • Reconnect to the same child — a child that lost its connection while still alive is in an unknown state; the listener accepts exactly one client (D4.2); and after a timeout the channel can't be trusted, since a late reply would be read as the answer to the next request.
  • Retry the in-flight call on the new child — an event that crashed one child crashes the next one the same way.
Reasoning

One recovery path covers every way a child can fail, and it is cheap because the state lives in the host. This is distinct from D5.3: a trap is caught inside the child, which keeps its previous generation and stays connected; a lost connection means the whole child, previous generation included, is gone.

Consequences

Without a limit, a state or a module that crashes the child on start would be respawned forever; D5.9 sets it.

D5.9

At most 3 restarts in 10 seconds, then the app stops until the next rebuild

accepted

A recovery (D5.3) and a respawn (D5.8) both count as restarts. Beyond 3 within any 10 seconds, the host stops restarting, logs why, and waits: the next successful rebuild starts the app again with the count cleared, as a successful reload also clears it. A persistent run sets its state trace aside then (D8.5).

Alternatives considered
  • Erlang/OTP's default, 1 restart in 5 seconds — the precedent this follows, too strict while editing: a couple of crashes while trying a change would stop the app.
  • Restart forever — a module or state that crashes on start would spin the child, and the log, without end.
Reasoning

This is OTP's restart intensity: a supervisor that sees too many restarts in a window gives up and escalates. Here the escalation is the developer: what fixes an app that keeps crashing is a code change, so a rebuild is what starts it again.

D5.10

While the app can't answer, its last frame stays with a notice, and Ctrl+C quits

accepted

While a subprocess is respawning or the app is stopped, the host keeps drawing the last view the app built, with a line at its bottom saying which: restarting, or stopped until the next rebuild. Input doesn't reach the app then, except Ctrl+C, which quits the host.

Alternatives considered
  • A blank screen or an error page — loses what the app showed, which is often what explains the crash.
  • Leave quitting to the app's own key — it can't be reached while the app isn't running, which leaves killing the terminal.
