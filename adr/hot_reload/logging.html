Domain 6

Log separation

Four destinations, not two — and why a passing concurrency stress test is evidence, not a guarantee.

D6.1

Four separate destinations: terminal, IPC channel, framework log, app log — never sharing a stream

accepted

The rendered TUI lives exclusively on the outer host's real stdin/stdout. The IPC channel is a dedicated named pipe (D4.2) and carries nothing else; the subprocess's own stdin/stdout/stderr are not part of it and are set to null (D4.4). Framework diagnostics and app-emitted log lines both go somewhere that is neither the terminal nor the pipe.

Reasoning

"Separate stdout and stderr" sounds like enough streams until you notice they can still both end up attached to the same terminal the TUI is rendering into. Two streams isn't the same as two destinations; the real requirement is destinations, and there turn out to be four of them once the subprocess exists. Putting the protocol on its own pipe rather than on the child's stdio is what keeps the IPC destination from being something a stray print can reach.

D6.2

Framework and app logs share one tagged file, not per-source files or a spawned terminal

accepted

Both write [framework:host]/[framework:child]/[app]-tagged lines to the same file, opened directly (never via inherited/piped stdio).

Alternatives considered
  • Separate log files per source. Loses the one thing a single file gives for free: chronological interleaving between "host says it's rebuilding" and "app says its state just reset" — two files force manually cross-referencing timestamps.
  • Spawn a second terminal window for live log viewing. Heavier, platform-specific (a different spawn mechanism per OS/terminal emulator), and breaks over SSH or in any headless environment — not standard practice for a TUI tool.
Reasoning

This is also, independently, a live bug fix: the framework's own current eprintln!("[termoxide_hot_reload] ...") diagnostics write to real stderr today, and only looked clean throughout this project's own testing because every test redirected via 2>&1 | tee <file>. Run any current draft in an unredirected terminal and those lines corrupt the alternate-screen display.

D6.3

A log line is committed under cross-process exclusion, not on the assumption that one write_all is one write

accepted

Any process appending to the shared log file formats a complete line first, then writes it while holding an exclusive cross-process lock on the log file for the entire write. The lock is held only for that one line's write, never across user code. A single write_all call, on its own, is not sufficient.

Alternatives considered
  • One write_all per line, no lock — what this decision originally said. Rejected: it relies on a single call being a single syscall, which the standard library does not promise (see Reasoning).
  • Route every record through a single writer that owns the file, so there is only ever one appender. Valid, and it would remove the need for a lock — but here the only way for the subprocess to reach the host's writer is the IPC channel, which D4.2 reserves exclusively for the protocol. Carrying log records over it would blur the four-destination separation in D6.1 and make logging depend on the host being responsive.
Reasoning

O_APPEND/FILE_APPEND_DATA makes "seek to end + write" atomic per syscall, so two processes writing concurrently never clobber each other's file offset. That is all it guarantees. It does not make a logical line atomic, and Write::write_all is specified to call write in a loop until the whole buffer is written — so after a short write, one write_all call becomes several syscalls, and another process can append between them and split the line. Short writes to a local regular file are rare, but they are permitted behaviour, not a bug, and larger lines and non-local filesystems make them more likely.

A concurrency stress test was run: two real, uncoordinated OS processes each wrote 20,000 lines to the same file concurrently, one write_all per line. Result: 40,000 lines, zero malformed, all present and distinct, on this project's actual Windows/NTFS setup. Treat that as evidence the common path behaves, not as proof of the guarantee — a short write is exactly the case a run like that is unlikely to hit, so a clean result cannot exclude it.

Consequences

A process killed while holding the lock does not wedge logging: the operating system releases file locks when the holding process exits, so the hang-recovery in D5.7 and the subprocess kill in D4.1 stay safe with respect to the log. Lines are still tagged per source (D6.2); the lock only orders the writes, it does not merge them.

This is a property of the writing discipline, not of shared append-mode files in general — which is why D6.4 routes the app's output through a framework-owned sink that takes the same lock, rather than trusting the app's own write pattern.

D6.4

App-side logging goes through a framework-owned sink, never .inherit_stdio()

deferred

The app's stdout/stderr (once WASI is wired at all — see Domain 7) point at a custom writer the framework controls, not at a real inherited file descriptor. That writer buffers arbitrary partial writes internally and commits each completed line under the same exclusive lock as every other writer (D6.3), regardless of how many separate print!/write! calls the app makes.

Alternatives considered
  • WasiCtxBuilder::inherit_stdio() — wires the guest's fds directly to whatever the subprocess's own stdio currently is. That used to be the IPC channel, which made this actively destructive; with the protocol on its own named pipe (D4.2) it can no longer corrupt the protocol, but it is still rejected. The subprocess's stdio is null (D4.4), so inheriting it would silently discard every line of app output, and it bypasses the framework sink and the lock D6.3 requires — the app's output would never reach the log file under the one writer discipline.
Reasoning

Raw println!/eprintln! were confirmed live to compile but silently no-op at runtime on wasm32-unknown-unknown with no WASI wired — no output, no panic, no error. Once WASI stdio is wired (D7.1), the correctness burden for D6.3 has to live in the sink implementation, not in a convention the app author is expected to follow — the whole point of D1.3 is not restricting what the app author writes, so the framework absorbs the discipline instead.

Ordinary Rust logging (the log crate's info!/warn! macros) is preferred over raw print! for app code generally: the framework can install a log::Log backend once, inside the same macro that generates the rest of the app's exports, and the app author never has to know the transport underneath is a custom sink rather than a real stdout.
