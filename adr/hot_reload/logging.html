Domain 6

Log separation

Four destinations, not two — and the one thing verified with a real concurrency stress test rather than cited from documentation.

D6.1

Four separate destinations: terminal, IPC channel, framework log, app log — never sharing a stream

accepted

The rendered TUI lives exclusively on the outer host's real stdin/stdout. The subprocess's stdin/stdout are the IPC channel (D4.2) and carry nothing else. Framework diagnostics and app-emitted log lines both go somewhere that is neither of those two.

Reasoning

"Separate stdout and stderr" sounds like enough streams until you notice they can still both end up attached to the same terminal the TUI is rendering into, or — once a subprocess is in the picture — attached to the one pipe carrying the actual protocol. Two streams isn't the same as two destinations; the real requirement is destinations, and there turn out to be four of them once the subprocess exists.

D6.2

Framework and app logs share one tagged file, not per-source files or a spawned terminal

accepted

Both write [framework:host]/[framework:child]/[app]-tagged lines to the same file, opened directly (never via inherited/piped stdio).

Alternatives considered
  • Separate log files per source. Loses the one thing a single file gives for free: chronological interleaving between "host says it's rebuilding" and "app says its state just reset" — two files force manually cross-referencing timestamps.
  • Spawn a second terminal window for live log viewing. Heavier, platform-specific (a different spawn mechanism per OS/terminal emulator), and breaks over SSH or in any headless environment — not standard practice for a TUI tool.
Reasoning

This is also, independently, a live bug fix: the framework's own current eprintln!("[termoxide_hot_reload] ...") diagnostics write to real stderr today, and only looked clean throughout this project's own testing because every test redirected via 2>&1 | tee <file>. Run any current draft in an unredirected terminal and those lines corrupt the alternate-screen display.

D6.3

Every writer commits exactly one OS write per log line

accepted

Any process appending to the shared log file must format a complete line first, then issue one write_all — never multiple partial writes per line.

Reasoning

O_APPEND/FILE_APPEND_DATA makes "seek to end + write" atomic per syscall, so two processes writing concurrently never clobber each other's file offset — but that guarantee is per-syscall, not per-logical-line. A line built from several separate writes (tag, then message, then newline) can be interleaved by another process's write landing in the middle.

Verified directly, not assumed: two real, uncoordinated OS processes wrote 20,000 lines each to the same file concurrently, each committing one write_all per line. Result: 40,000 lines, zero malformed, all present and distinct — on this project's actual Windows/NTFS setup, not cited from POSIX documentation that may not transfer.

Consequences

This is a property of the writing discipline, not of shared append-mode files in general. If the app's own code (via D6.4) ever wrote multiple raw partial writes to its log target, this guarantee would not hold for those lines — which is exactly why D6.4 puts a buffering layer between the app and the file rather than trusting the app's own write pattern.

D6.4

App-side logging goes through a framework-owned sink, never .inherit_stdio()

deferred

The app's stdout/stderr (once WASI is wired at all — see Domain 7) point at a custom writer the framework controls, not at a real inherited file descriptor. That writer buffers arbitrary partial writes internally and commits one real file write per completed line (satisfying D6.3) regardless of how many separate print!/write! calls the app makes.

Alternatives considered
  • WasiCtxBuilder::inherit_stdio() — wires the guest's fds directly to whatever the subprocess's own stdio currently is, which is the IPC channel (D4.2). Splices arbitrary app text directly into the protocol stream. Rejected outright, not just discouraged.
Reasoning

Raw println!/eprintln! were confirmed live to compile but silently no-op at runtime on wasm32-unknown-unknown with no WASI wired — no output, no panic, no error. Once WASI stdio is wired (D7.1), the correctness burden for D6.3 has to live in the sink implementation, not in a convention the app author is expected to follow — the whole point of D1.3 is not restricting what the app author writes, so the framework absorbs the discipline instead.

Ordinary Rust logging (the log crate's info!/warn! macros) is preferred over raw print! for app code generally: the framework can install a log::Log backend once, inside the same macro that generates the rest of the app's exports, and the app author never has to know the transport underneath is a custom sink rather than a real stdout.
