Domain 10

Forward compatibility

Three framework-wide goals that aren't solved here — and confirmation that nothing decided in this record forecloses any of them.

D10.1

Partial/diff-based redraw is a wire-format change, not an architectural one

deferred

build_view re-serializes the entire frame on every call today. Diffing — the guest tracking its own previously-rendered frame and returning only changed lines — would be an ordinary evolution of the wire format (same category as any other change in Domain 3), not something the transport, subprocess, or hang-protection layers need to know about.

Reasoning

An earlier draft of this reasoning leaned on ratatui's own internal buffer diffing as evidence the problem was "already solved" — confirmed live, that diffing genuinely happens today, cursor-repositioning and single-character writes rather than full-screen redraws. But that's a property of one specific rendering backend, not of this architecture, and stops being true the moment the backend isn't guaranteed to be ratatui (D10.2). If diffing is ever built to survive backend choice, it has to live in termoxide_rendering itself, computing the diff between successive ViewNode trees backend-independently — not delegated to whatever the active backend happens to do internally.

A trap during a diff-computing build_view is exactly as atomic and recoverable as one during a full-frame call (D2.3) — host either gets a complete update or an error, never a half-applied frame, regardless of whether that update is a diff or a full frame.

Consequences

If built: recommended default is guest-side "last frame" state, reset to full-redraw immediately after every reload rather than threaded through persistence — a reload is rare and human-paced, so one full-frame redraw right after a swap is free in practice.

D10.2

Backend-agnosticism is a termoxide_rendering concern this record doesn't touch, but doesn't block either

deferred

The app-facing boundary (Domain 3) never mentions ratatui — the guest only ever returns the framework's own minimal Color/Line types. What's still coupled to ratatui specifically is termoxide_rendering's own Renderer/Style types, which predate this record entirely.

Reasoning

This is a direct, if previously unstated, consequence of D2.3 ("guest computes data, host renders"): a guest that called a specific backend's API directly would have hard-wired every app to it, unfixable without recompiling every app built on this framework. Making the guest backend-blind is what leaves the door open for host to swap backends later, behind a RenderBackend-shaped trait termoxide_rendering would need to be generic over (ratatui/crossterm/other, via Cargo feature) — separate, pre-existing work this record neither does nor blocks.

D10.3

Multithreading and async events need the host loop restructured, using patterns already proven elsewhere in this codebase

deferred

The host loop as built (drive(), every wasm/dylib draft) is one synchronous while loop on one thread — rebuild check, event poll, tick, render, sequentially — and the rebuild step specifically still blocks it.

Reasoning

Not a consequence of choosing wasm, a subprocess, or IPC — this codebase already has the opposite pattern elsewhere: termoxide_event's input reading runs on its own background thread, and the hot-lib-reloader draft's rebuild watcher already runs via std::thread::spawn, decoupled from its main loop. It's specifically the wasm/dylib-framework hosts that didn't carry that pattern over for their rebuild step.

If anything, the subprocess in Domain 4 makes this easier, not harder: pipe-based IPC (ChildStdin/ChildStdout) is exactly what async runtimes like tokio are built around, where today's in-process wasm call is a plain blocking function call with no async story of its own. wasmtime also has a directly relevant built-in option, but it takes more than turning on async. Cooperative yielding needs all of: Config::async_support(true) and calling the guest via .call_async(); Config::consume_fuel(true) with fuel actually supplied to the store; and Store::fuel_async_yield_interval(...) set to a yield interval. async_support and .call_async() alone do not make a guest yield — without periodic yielding, a compute-bound guest simply blocks the executor for the duration of a future poll.

The yield interval and the total fuel budget are two separate settings, and only one of them is a hang bound: the interval makes a long call yield back to the executor periodically and resume, while exhausting the total budget (D5.1) still traps. So hang protection and async-friendliness share the same fuel accounting, but they are configured separately and answer different questions — "let other tasks run" versus "stop this call."
