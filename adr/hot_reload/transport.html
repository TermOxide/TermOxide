Domain 2

Transport: why wasm

Three transports were drafted and live-tested end to end before this call was made. This is what each one actually cost, and the one property that decided it.

D2.1

wasm (via wasmtime) is the shipped hot-reload transport

accepted

logic compiles to wasm32-unknown-unknown and runs inside a wasmtime instance. A file save triggers a rebuild; the new module is loaded and swapped in without restarting the host process.

Alternatives considered
  • Full process restart (the naive approach) — kill the whole host process on every change, rebuild, respawn. This project's own earliest drafts (process-supervisor, watchexec-supervisor) worked exactly this way, with a blue/green output-file swap to dodge Windows' file lock on a running binary. It's the simplest possible mechanism, and the only one of the four options where the app visibly disappears from the terminal for the whole rebuild — the same cargo build duration every other option pays in the background, but spent with nothing running at all, instead of the previous generation staying up throughout.
  • dylib-view-swap — logic builds as a native cdylib, loaded via libloading. Fastest at runtime (no sandbox indirection), but libloading::Library::get only checks that a symbol name exists, never that its signature matches — a stale build loaded against a newer host's expectations is silent undefined behavior, not a caught error. See D2.2.
  • hot-lib-reloader — same native-dylib idea, but using the hot-lib-reloader crate's #[hot_module]/hot_functions_from_file! machinery instead of hand-rolled libloading. Real Rust types cross the boundary (same-toolchain trust), which is the cheapest possible app-author surface — but it inherits the same unchecked-signature risk as dylib-view-swap, and gets none of wasm's execution-level protections (D5.1).
Reasoning

All four were built or drafted to be compared on the same basis rather than on convenience: does the app stay running, does a function-signature mismatch fail safely, can a guest's infinite loop be bounded without its cooperation. Full process restart loses the first property outright — every edit costs all in-memory state, not just the rebuild time. Of the three that keep the process alive, wasm won on properties that generalize past hot-reload itself: it fails safe on a function-signature mismatch with zero extra code (D2.2 — the byte-level schema needs its own check, D3.4), and it's the only one where a guest's infinite loop can be bounded without any cooperation from the guest's own code (D5.1). Both dylib forms would need hand-built mitigations to match either property.

Consequences

The standing cost is the wasmtime dependency and a sandbox indirection (linear-memory read/write instead of a direct pointer) on every call. Measured against a typical TUI's actual workload — a handful of calls per frame, a few hundred bytes to ~2KB of state each — this is noise next to terminal I/O itself, not a load-bearing performance concern.

wasm32's linear memory address space is 32-bit, which caps the whole guest — the entire TUI app's in-memory state and working data, not just the hot-reload machinery — at 4GiB. This is a hard architectural ceiling of the transport, not a configurable limit, and it applies to any app built on this framework, not just today's demos. It is nowhere close to binding today (this framework's own wire-format buffers are kilobytes), but it is a real constraint this choice accepts, not a hypothetical one.

D2.2

An ABI-drift failure must be a caught error, not undefined behavior

accepted

If the app's exported function signatures ever drift from what host expects — a stale build, an in-flight ABI change — loading it must fail cleanly and recoverably, never corrupt memory or crash silently. This covers function types only; it says nothing about what the bytes passed through linear memory mean, which is a separate check (D3.4).

Reasoning

wasmtime's Instance::get_typed_func::<Params, Results> validates the requested Rust signature against the module's actual declared type at load time and returns Err on a mismatch — the surrounding reload logic already treats a load failure as "keep the currently running generation, log the error" (D5.4). This is inherent to how wasmtime resolves typed exports, not something built for this project.

The native-dylib alternatives have no equivalent: libloading::Library::get::<T> is an unchecked unsafe cast from a symbol name to a function-pointer type. A signature mismatch there means the call interprets the wrong number or type of arguments off the stack.

Consequences

This is the deciding property in D2.1, and it is real but narrower than it first looks. A change to an exported function's signature gets this safety net automatically, on every app, with no per-change discipline required. A change to what the bytes mean — a reordered tag table, a changed line encoding, a different buffer capacity, an edited state type — does not: a stale guest can keep identical function types while changing the meaning of everything that crosses the boundary through linear memory, and both sides will decode successfully into wrong values. That surface needs its own check (D3.4 for the framework's wire format, D3.7 for app state). The comparison against the native-dylib options in D2.1 still stands — they have neither check — but wasm gets one of the two for free, not both.

D2.3

The guest computes data; only the host ever touches the terminal

accepted

build_view returns a description of what should be on screen (styled lines). It never calls a rendering backend's API directly, never enters raw mode, never owns the alternate screen. All of that lives in the host process, unconditionally, on every transport.

Alternatives considered
  • Let the swapped code own terminal state directly — cheaper to reach for terminal-level features, since the guest could just call the rendering library itself.
Reasoning

None of core wasm's capabilities include real terminal control (no WASI-standardized terminal ioctl), so a wasm guest couldn't reach the terminal directly without inventing a large, non-standard host-import surface reimplementing the rendering backend's whole API as imports. More importantly: if a reload swapped code that held partial raw-mode/alternate-screen state, recovering from a crash mid-render would mean recovering the terminal's own broken state, not just discarding a bad generation.

This also happens to be what makes backend-agnosticism possible at all (D10.2) — a guest that called one specific backend's API would hard-wire every app to it.

Consequences

A trap or hang during build_view is atomic from the terminal's perspective: host either has a complete new frame to draw, or an error and redraws the previous one. There is no partially-rendered state possible, on any transport.
