Domain 3

The app contract (ABI)

What an app author actually writes, what crosses the boundary, and why there's no hand-maintained wire format anywhere in it.

D3.1

The entire app-author surface is a state type plus three functions

accepted

on_tick(&mut State), handle_event(&mut State, Event) -> bool, build_view(&State, width, height) -> Vec<Line>. No host code, no FFI, no manual export list. A single macro invocation (wasm_app!(App)) generates every low-level export from an implementation of this trait.

Reasoning

Every existing draft (dylib, wasm, hot-lib-reloader) converged on this exact shape independently, which is what made comparing them on equal footing possible (D2.1). It's also the smallest surface that still lets the framework own the render loop, the reload machinery, hang protection, and logging entirely on the host side.

D3.2

State crosses the boundary as postcard-encoded bytes, generic over any app-defined type

accepted

The app's state type needs exactly one thing beyond being a plain struct: #[derive(Serialize, Deserialize)]. The macro's generated exports handle encode/decode internally — no hand-rolled wire format, no fixed-size #[repr(C)] struct kept in sync by hand.

Alternatives considered
  • Hand-defined #[repr(C)] structs (what the original dylib-view-swap draft did) — both sides must keep every field in sync by hand, on pain of undefined behavior if they ever drift.
Reasoning

The app author should not have to hand-maintain a byte-for-byte struct layout, so the framework generates the encoding instead. postcard handles arbitrary Serialize types generically; the macro calls it the same way for every app. This trades a hand-kept layout for a generated one — it does not make schema drift disappear, which is why D3.4 and D3.7 exist.

D3.3

The outer host holds the app's state as an opaque byte blob, with its last few generations, and never deserializes it

accepted

Only the guest ever decodes state into the app's real Rust type. The outer host — the process that owns the terminal, not the subprocess (D4.1) — holds the Vec<u8>, passes it in on every call, unexamined, and never needs a type parameter for the app's state at all. It keeps the last few generations of that blob, between two and five (the exact number is open), so a respawned subprocess (D5.8) starts from the host's copy rather than from Default, and a state that keeps crashing the child can be stepped back to an earlier, stable one.

Reasoning

This falls out of D3.2 rather than being separately designed: since encoding already has to happen for the guest to receive its state at all, there's nothing left for host to gain by also decoding it. The practical payoff shows up in D8.2 — persisting that same opaque blob to disk needs no new encoding step.

Consequences

The copy that matters lives in the process that survives a subprocess crash. Every call that changes state therefore has to return the new blob to the host; otherwise the host's copy lags behind and a respawn loses the difference.

D3.4

A wire-schema version is checked before a generation is accepted, in addition to the function-signature check

accepted

The guest exports a wire-schema version (or a fingerprint derived from the schema) covering everything that crosses the boundary as bytes: the tag tables (Color, KeyCode, modifier bits, event kinds), the line encoding, the buffer capacities, and the state-encoding convention. Host compares it against its own expected value before resolving anything else, and a mismatch rejects the generation through the same path as a failed rebuild (D5.4). A fingerprint generated at build time removes the "remember to bump it" discipline; which of the two is used is left open.

Alternatives considered
  • Rely on get_typed_func alone — what this entry originally said, on the grounds that a version export "would only improve the error message." That was wrong. Rejected: a function's type is not the schema of the bytes passed through linear memory.
Reasoning

A stale guest and a current host can agree on on_tick(i32) -> i32 exactly while disagreeing on what tag 3 means for Color, how a line is length-prefixed, or how large the output buffer is. Both sides then decode successfully into wrong values — no trap, no error, nothing for D2.2's check to see. Serialization formats make this worse, not better: postcard is not self-describing, encoding structs positionally with no field names and enum variants by discriminant, so reordering or inserting a variant decodes successfully as the wrong one rather than failing.

Since host and guest are both built from the same shared abi crate, a stale guest is simply one built against an older revision of it — which is precisely the situation a hot-reload loop produces whenever the framework itself is edited.

Consequences

This covers the framework's own types. It deliberately does not cover the app's state type, which changes whenever the app author edits it and needs different handling (D3.7). For the native-dylib alternatives (D2.1) this check would have been the only safety net, since they have no function-signature check either. Not built on any draft.

D3.5

Styling in the wire format needs to grow before this is more than a demo

unverified

The Color type crossing the boundary today is a five-value enum (default/cyan/yellow/green/magenta) — a placeholder, not RGB or the bold/italic/underline/dim/strikethrough/background attributes a real backend exposes.

Reasoning

This is the same category of change as any other ABI evolution in this domain (D2.2 already covers what happens if host and a stale guest disagree about it) — not an architectural question, just not done. Marked unverified rather than deferred because the eventual shape depends on D10.2's backend-abstraction work landing first, so the "richer Color" shape shouldn't be locked in before that's settled.

D3.6

The same wasm_app!(App) invocation produces either path, switched on cfg(target_arch = "wasm32")

accepted

The app author's source never changes between dev and release — one impl WasmApp for App, one wasm_app!(App) call. The macro expands to the wasm export/marshaling machinery (the rest of this domain) when compiled for wasm32, and to a near-empty native bridge otherwise; the compiler keeps only the branch matching the active target.

Alternatives considered
  • Gate on cfg(debug_assertions) (release/debug profile) instead of target — rejected. A release-profile wasm32 build (optimized logic, still run through the dev hot-reload loop for speed during iteration) still needs the wasm export path, so profile is the wrong signal. Target architecture is the actual fact that distinguishes the two worlds, and Cargo already sets it from --target without anyone needing to flip it by hand.
Reasoning

Native linking needs no named-symbol export or runtime resolution at all — once logic is just another crate in the same compilation graph, the host's native entry point can be an ordinary generic function, run_native::<A: WasmApp>(), calling A::on_tick(&mut state) directly. There is nothing for the macro's native branch to generate beyond what the app's own trait impl already provides.

Consequences

logic's crate-type needs to list both cdylib (the artifact the dev path loads) and rlib (so the native host can depend on it as an ordinary crate) — not a new risk: the hot-lib-reloader draft already uses the equivalent dual declaration (["rlib", "dylib"]) for the same reason, one level native rather than wasm. Not built on any draft.

D3.7

App state carries a schema fingerprint; a mismatch is never silently decoded and never silently reset

accepted

Host holds the app's state as opaque bytes (D3.3) and hands them to whichever generation is loaded. If the app author edits the shape of their state type — adds, removes, reorders or retypes a field — those bytes no longer mean what the new generation expects. The blob therefore carries a state-schema fingerprint produced by the guest. On a mismatch the new generation does not decode it: state is reset to its default and a notice is written to the log (Domain 6). Migration between shapes is out of v1.

Alternatives considered
  • Decode and hope — worst outcome. postcard is positional and not self-describing, so changed bytes can decode successfully into wrong values, silently corrupting state rather than failing.
  • Fall back to Default on a decode error — what the drafts' generated decode does today (postcard::from_bytes(bytes).unwrap_or_default()). It loses state with no signal when decoding fails, and does nothing about the case where decoding succeeds wrongly.
  • Reject the generation and keep the previous one (D5.4) — safe, but it makes editing the state type impossible without restarting the host, which is the very edit that most often needs a reload.
  • Author-supplied migration functions — the right long-term answer for keeping state across a shape change; deferred, not designed here.
Reasoning

The promise in D1.1 — the running app survives an edit with its state — holds only while the state type's shape is unchanged. The honest alternative to pretending otherwise is to make the loss visible and bounded: reset deliberately, say so, and never feed a generation bytes it will misread.

Consequences

The generated decode must not use unwrap_or_default(); it must distinguish "fingerprint mismatch" from "decode failure" and report both. Persistence (Domain 8) has the same problem across a host restart: a snapshot written by an older build must carry the fingerprint too, or a stale snapshot is decoded wrongly after the author changes the type. Not built on any draft.
