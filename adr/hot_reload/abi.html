Domain 3

The app contract (ABI)

What an app author actually writes, what crosses the boundary, and why there's no hand-maintained wire format anywhere in it.

D3.1

The app-author surface is termoxide's own App trait

accepted

A hot-reloaded app implements the same App trait as a native one — track_view, on_tick, handle_event(&self, Event) -> bool, build_view(&self, Rect) -> ViewNode — with its state in signals. No host code, no FFI, no manual export list. A single macro invocation (wasm_app!(Counter::default()), given how to build the app) generates every low-level export from that implementation.

Alternatives considered
  • A dedicated WasmApp trait, what this entry originally said: a state type plus three functions, on_tick(&mut State), handle_event(&mut State, Event) -> bool, build_view(&State, width, height) -> Vec<Line>. Every hot-reload draft converged on it, which is what made comparing them on equal footing possible (D2.1). Rejected: it is a second programming model beside the framework's own, so an app written for hot reload would not be a TermOxide app.
Reasoning

A spike built the framework's own types for wasm32-wasip1 and ran them in wasmtime: the reactive runtime runs in the guest on a local custom executor, a signal serializes as its value, and a view tree and the input events round-trip through postcard, with the same bytes on wasm32 and x86_64. What it ran into were dependencies, not the model: crossterm doesn't build for WASI (D3.8), and ratatui's colours can't be decoded by postcard (D3.5).

Consequences

The guest runs the reactive runtime itself, so signals, effects and memos keep their native behaviour. The guest tells the host a repaint is due through a dirty flag on its replies (D4.5), set by track_view's render effect once the guest has let it run. The spike ran on wasip1; the guest now targets wasip2 (D2.1), where only the crates' builds are checked so far.

D3.2

State crosses the boundary as postcard-encoded bytes: the app value, its signals by value

accepted

The app's state is its App value. Its fields are signals, which serialize as their current values and deserialize as new signals holding them (termoxide_reactive's serde feature), so the app type needs exactly one thing beyond being a plain struct: #[derive(Serialize, Deserialize)]. The macro's generated exports handle encode/decode internally — no hand-rolled wire format, no fixed-size #[repr(C)] struct kept in sync by hand.

Alternatives considered
  • Hand-defined #[repr(C)] structs (what the original dylib-view-swap draft did) — both sides must keep every field in sync by hand, on pain of undefined behavior if they ever drift.
Reasoning

The app author should not have to hand-maintain a byte-for-byte struct layout, so the framework generates the encoding instead. postcard handles arbitrary Serialize types generically; the macro calls it the same way for every app. This trades a hand-kept layout for a generated one — it does not make schema drift disappear, which is why D3.4 and D3.7 exist.

D3.3

The outer host holds the app's state as an opaque byte blob, and never deserializes it

accepted

Only the guest ever decodes state into the app's real Rust type. The outer host — the process that owns the terminal, not the subprocess (D4.1) — holds the Vec<u8>, passes it in on every call, unexamined, and never needs a type parameter for the app's state at all. It keeps the latest blob, so a respawned subprocess (D5.8) starts from the host's copy rather than from Default. Whether it should keep a few earlier generations as well is open until there is data.

Alternatives considered
  • Keep the last few generations, between two and five — what this entry originally said, so a state that keeps crashing the child could be stepped back to an earlier, stable one. Not built yet: a crash right after a reload already goes back to the previous component with the latest state (D5.3), which covers the common case, and a state that crashes every generation stops the app (D5.9), its persisted trace set aside (D8.5). How often a state alone is the cause is not known yet.
Reasoning

This falls out of D3.2 rather than being separately designed: since encoding already has to happen for the guest to receive its state at all, there's nothing left for host to gain by also decoding it. The practical payoff shows up in D8.2 — persisting that same opaque blob to disk needs no new encoding step.

Consequences

The copy that matters lives in the process that survives a subprocess crash. Every call that changes state therefore has to return the new blob to the host; otherwise the host's copy lags behind and a respawn loses the difference. Only those calls do: the guest compares the encoded app with the last blob it sent, so a change to any of its signals counts, not only to those the view reads (D4.5).

D3.4

A wire-schema fingerprint is checked before a generation is accepted, in addition to the function-signature check

accepted

The guest exports wire-schema, a fingerprint of the protocol's request and reply types (D4.5), which hold everything that crosses the boundary as bytes: the event types, ViewNode, Color, the style. The subprocess compares it against its own on every generation, before any request, and a mismatch rejects the generation through the same path as a failed rebuild (D5.4). The fingerprint is traced from the types, never bumped by hand: serde-reflection traces each type's shape as serde sees it in a binary format, and a 64-bit FNV-1a hash of that trace is the fingerprint.

Alternatives considered
  • Rely on get_typed_func alone — what this entry originally said, on the grounds that a version export "would only improve the error message." That was wrong. Rejected: a function's type is not the schema of the bytes passed through linear memory.
  • A version number bumped by hand — left open by this entry at first. Rejected: it rests on remembering to bump it at every change to any type that crosses, which is exactly the slip it exists to catch.
  • std's hasher for the fingerprint — rejected: its algorithm may change between Rust releases, and a fingerprint has to mean the same thing to every build.
Reasoning

A stale guest and a current host can agree on on_tick(i32) -> i32 exactly while disagreeing on what tag 3 means for Color, how a line is length-prefixed, or how large the output buffer is. Both sides then decode successfully into wrong values — no trap, no error, nothing for D2.2's check to see. Serialization formats make this worse, not better: postcard is not self-describing, encoding structs positionally with no field names and enum variants by discriminant, so reordering or inserting a variant decodes successfully as the wrong one rather than failing.

Since host and guest are both built from the same shared abi crate, a stale guest is simply one built against an older revision of it — which is precisely the situation a hot-reload loop produces whenever the framework itself is edited.

Consequences

This covers the framework's own types. It deliberately does not cover the app's state type, which changes whenever the app author edits it and needs different handling (D3.7). For the native-dylib alternatives (D2.1) this check would have been the only safety net, since they have no function-signature check either. The tracer's registry is taken unchecked: nested enums only get their variants' names and order resolved, which is all a fingerprint needs, where a checked registry would need every nested enum traced by hand.

D3.5

Views cross as ViewNode trees, with colours in the framework's own Color

accepted

The tree build_view returns crosses as postcard bytes, through the serde features of termoxide_rendering and termoxide_event. Colours cross as termoxide_layout's Color: named, RGB or indexed. A node's style and area are still ratatui's Style (with its Modifier) and Rect, as stand-ins: the resolved style replaces Style once it exists, with FontStyle taking over from Modifier, and a framework rect replaces Rect. Each swap is a wire-format change, caught by D3.4. ViewContent::Raw is removed.

Alternatives considered
  • ratatui's own serde for its colours — rejected. Its Color serializes as text and deserializes through an untagged enum, which needs a self-describing format: postcard can't decode it, and Rust's orphan rule forbids replacing another crate's implementation.
  • A wire-only copy of ratatui's colour, style and cell types — rejected: a duplicate kept in sync by hand, when the framework already has a Color.
  • A self-describing format (CBOR, MessagePack), so ratatui's serde works — not chosen: larger, slower frames and colours as text, against D3.2.
  • Keep Raw nodes, drawn in the guest and sent as their cells — rejected: a closure can't cross, and drawing ratatui widgets ties apps to ratatui rather than to the framework's view.
Reasoning

This entry used to be a placeholder: a five-value Color and styled Lines, to be enriched once the backend work settled. With the framework's own view crossing (D3.1), the vocabulary is the framework's. ratatui's Style stays only because the resolved style it stands in for is not built yet.

Consequences

Underline colours don't cross: ratatui only has them with its underline-color feature, which needs crossterm, so a wasm guest has no such field. FontStyle has no REVERSED, HIDDEN or RAPID_BLINK; the resolved style has to settle those before it replaces Modifier.

D3.6

The same wasm_app! invocation produces either path, switched on cfg(target_arch = "wasm32")

accepted

The app author's source never changes between dev and release — one impl App, one wasm_app! call. The macro expands to the wasm export/marshaling machinery (the rest of this domain) when compiled for wasm32, and to nothing otherwise; the compiler keeps only the branch matching the active target.

Alternatives considered
  • Gate on cfg(debug_assertions) (release/debug profile) instead of target — rejected. A release-profile wasm32 build (optimized logic, still run through the dev hot-reload loop for speed during iteration) still needs the wasm export path, so profile is the wrong signal. Target architecture is the actual fact that distinguishes the two worlds, and Cargo already sets it from --target without anyone needing to flip it by hand.
Reasoning

Native linking needs no named-symbol export or runtime resolution at all — once logic is just another crate in the same compilation graph, the host's native entry point can be termoxide's own run_with_app(app), the loop a native app already runs. There is nothing for the macro's native branch to generate beyond what the app's own trait impl already provides.

Consequences

logic's crate-type needs to list both cdylib (the artifact the dev path loads) and rlib (so the native host can depend on it as an ordinary crate) — not a new risk: the hot-lib-reloader draft already uses the equivalent dual declaration (["rlib", "dylib"]) for the same reason, one level native rather than wasm. The dev side is built; linking natively for release is not.

D3.7

App state carries a schema fingerprint; a mismatch is never silently decoded and never silently reset

accepted

Host holds the app's state as opaque bytes (D3.3) and hands them to whichever generation is loaded. If the app author edits the shape of their state type — adds, removes, reorders or retypes a field — those bytes no longer mean what the new generation expects. The blob therefore starts with a state-schema fingerprint produced by the guest, traced from the app's type like D3.4's. On a mismatch the new generation does not decode it: it starts from the app as built, says so in its reply, and a notice is written to the log (Domain 6). Migration between shapes is out of v1.

Alternatives considered
  • Decode and hope — worst outcome. postcard is positional and not self-describing, so changed bytes can decode successfully into wrong values, silently corrupting state rather than failing.
  • Fall back to Default on a decode error — what the drafts' generated decode does today (postcard::from_bytes(bytes).unwrap_or_default()). It loses state with no signal when decoding fails, and does nothing about the case where decoding succeeds wrongly.
  • Reject the generation and keep the previous one (D5.4) — safe, but it makes editing the state type impossible without restarting the host, which is the very edit that most often needs a reload.
  • Author-supplied migration functions — the right long-term answer for keeping state across a shape change; deferred, not designed here.
Reasoning

The promise in D1.1 — the running app survives an edit with its state — holds only while the state type's shape is unchanged. The honest alternative to pretending otherwise is to make the loss visible and bounded: reset deliberately, say so, and never feed a generation bytes it will misread.

Consequences

The decode tells "fingerprint mismatch" apart from "decode failure": state with the right fingerprint that still fails to decode is an error, which rejects the generation, not a reset. Persistence (Domain 8) has the same problem across a host restart; every entry of its state trace holds the fingerprint, so a trace written by an older build is caught the same way.

D3.8

The guest compiles against the framework's crates with default-features = false

accepted

termoxide, termoxide_event and termoxide_rendering put the terminal — crossterm, the renderer, the input reader and the run loop — behind a terminal feature, on by default. Without it they leave the App trait, ViewNode and the event types, which build for the guest's target (D2.1). CI builds every changed crate that way.

Alternatives considered
  • A separate termoxide_core crate holding the app-facing types, re-exported from their old crates — drafted and rejected: it moved files across crates and gave every type a second home, for what a feature does in place.
Reasoning

crossterm doesn't build for WASI, and every app-facing type lived in a crate that depended on it.

Consequences

The terminal-off build is a second configuration to keep compiling; CI's wasm leg guards it, skipping the e2e tests and the hot-reload host, which are native by design. ratatui stays a guest dependency, without crossterm, until D3.5's stand-ins are replaced.

D3.9

The component exports handle, carrying the encoded request, and its wire schema

accepted

The guest's WIT world exports handle: func(request: list<u8>) -> result<list<u8>, string> and wire-schema: func() -> u64 (D3.4), and imports log: func(level: level, message: string) (D6.4). handle takes a postcard-encoded request of the protocol (D4.5) and returns the encoded response, so the subprocess forwards the pipe's messages to the component unchanged.

Alternatives considered
  • One export per call (start, event, tick, build-view), what SPEC §2.1 listed for the core-module ABI. Each gets a typed signature check of its own (D2.2), at the cost of more WIT to keep in sync and a subprocess that translates every message. Rejected: every argument is bytes either way, so the typed check catches little.
Reasoning

The protocol already has one request enum and one reply enum; a component that takes them whole leaves the subprocess nothing to know about the app, and the guest reuses the same request handling as a native run.

Consequences

D2.2's check covers handle's signature only: what the bytes mean rests entirely on the wire-schema check, D3.4.

D3.10

termoxide_hot_reload has two explicit features, host and guest

accepted

host holds what the executable needs: the terminal side, the pipe, the log file, wasmtime and building the guest (D4.6). guest holds what the component needs: running the app and answering requests, its executor, its logger. What neither gates is the protocol both share. The app's crate enables host for its executable and guest for its cdylib.

Alternatives considered
  • One feature and its absence (guest and not(guest)) — rejected: it doesn't say what the other side needs, where two named features state each process's needs.
Consequences

Built with neither feature, the crate is only the shared protocol, which also builds for wasm; CI's wasm leg checks it.

D3.11

A signal's type says whether its changes are recorded

accepted

Signal<T, R = Recorded>: a change to a recorded signal adds an entry to a persistent run's state trace (D8.4), a change to an Unrecorded one doesn't, though its value still goes wherever the state goes and the next recorded entry includes it. Signal::new is the only constructor and makes a recorded signal; .unrecorded() and .recorded() turn a handle into the other type. The guest tells the two kinds of change apart by also encoding the app with every unrecorded signal written as ().

Alternatives considered
  • A field on the signal, set at creation — what was asked for first. Rejected: state is restored by rebuilding each signal from its value, so a field that isn't serialized is lost at every reload, restart and persisted start.
  • The field, serialized next to the value — survives a restore, but the restored state carries the old flag, so changing it in the source would only take effect after a fresh start.
  • A generic constructor, Signal::with_mode::<R>(value) — works, but a second way to make a signal; new stays the one entry point, the mode a step after it.
  • A runtime switch to record a signal for a few lines — discussed, not built: the mode is read from the app's field type when the app is encoded, so it can't change at run time without keeping a value outside the type, which a reload would reset.
Reasoning

The mode has to outlast a signal rebuilt from its value, and the only thing that does is the code: the type the app stores the signal as. Rust picks a type's default parameters where a type is named, so impl Signal<T> is the recorded one and Signal::new needs no annotation.

Consequences

The mode holds for the field's whole lifetime: a handle turned into the other type still writes to the same signal, recorded or not as the app's field says. Both kinds serialize the same way and deserialize through the same code, so marking a signal unrecorded doesn't change the state fingerprint (D3.7).
