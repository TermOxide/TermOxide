Domain 3

The app contract (ABI)

What an app author actually writes, what crosses the boundary, and why there's no hand-maintained wire format anywhere in it.

D3.1

The entire app-author surface is a state type plus three functions

accepted

on_tick(&mut State), handle_event(&mut State, Event) -> bool, build_view(&State, width, height) -> Vec<Line>. No host code, no FFI, no manual export list. A single macro invocation (wasm_app!(App)) generates every low-level export from an implementation of this trait.

Reasoning

Every existing draft (dylib, wasm, hot-lib-reloader) converged on this exact shape independently, which is what made comparing them on equal footing possible (D2.1). It's also the smallest surface that still lets the framework own the render loop, the reload machinery, hang protection, and logging entirely on the host side.

D3.2

State crosses the boundary as postcard-encoded bytes, generic over any app-defined type

accepted

The app's state type needs exactly one thing beyond being a plain struct: #[derive(Serialize, Deserialize)]. The macro's generated exports handle encode/decode internally — no hand-rolled wire format, no fixed-size #[repr(C)] struct kept in sync by hand.

Alternatives considered
  • Hand-defined #[repr(C)] structs (what the original dylib-view-swap draft did) — both sides must keep every field in sync by hand, on pain of undefined behavior if they ever drift.
Reasoning

Once D2.2 established that signature mismatches already fail safe, there was no remaining reason to make the app author hand-maintain a byte-for-byte struct layout too. postcard handles arbitrary Serialize types generically; the macro calls it the same way for every app.

D3.3

Host holds the app's state as an opaque byte blob and never deserializes it

accepted

Only the guest ever decodes state into the app's real Rust type. Host passes the same Vec<u8> back in on every call, unexamined, and never needs a type parameter for the app's state at all.

Reasoning

This falls out of D3.2 rather than being separately designed: since encoding already has to happen for the guest to receive its state at all, there's nothing left for host to gain by also decoding it. The practical payoff shows up in D8.2 — persisting that same opaque blob to disk needs no new encoding step.

D3.4

An explicit ABI_VERSION export is optional, not required

deferred

A pub const ABI_VERSION: u32 exported as its own symbol, checked before resolving anything else, was considered as a way to turn an ABI mismatch into a clean error with a specific, readable message.

Reasoning

For the dylib transports this would have been close to mandatory — libloading gives no signature check at all (D2.2), so a hand-rolled version check would have been the only safety net available. For wasm, get_typed_func already fails safe automatically; an explicit version export would only improve the error message, not add a safety property that doesn't already exist. Worth building if diagnostics quality becomes a real complaint, not before.

D3.5

Styling in the wire format needs to grow before this is more than a demo

unverified

The Color type crossing the boundary today is a five-value enum (default/cyan/yellow/green/magenta) — a placeholder, not RGB or the bold/italic/underline/dim/strikethrough/background attributes a real backend exposes.

Reasoning

This is the same category of change as any other ABI evolution in this domain (D2.2 already covers what happens if host and a stale guest disagree about it) — not an architectural question, just not done. Marked unverified rather than deferred because the eventual shape depends on D10.2's backend-abstraction work landing first, so the "richer Color" shape shouldn't be locked in before that's settled.

D3.6

The same wasm_app!(App) invocation produces either path, switched on cfg(target_arch = "wasm32")

accepted

The app author's source never changes between dev and release — one impl WasmApp for App, one wasm_app!(App) call. The macro expands to the wasm export/marshaling machinery (the rest of this domain) when compiled for wasm32, and to a near-empty native bridge otherwise; the compiler keeps only the branch matching the active target.

Alternatives considered
  • Gate on cfg(debug_assertions) (release/debug profile) instead of target — rejected. A release-profile wasm32 build (optimized logic, still run through the dev hot-reload loop for speed during iteration) still needs the wasm export path, so profile is the wrong signal. Target architecture is the actual fact that distinguishes the two worlds, and Cargo already sets it from --target without anyone needing to flip it by hand.
Reasoning

Native linking needs no named-symbol export or runtime resolution at all — once logic is just another crate in the same compilation graph, the host's native entry point can be an ordinary generic function, run_native::<A: WasmApp>(), calling A::on_tick(&mut state) directly. There is nothing for the macro's native branch to generate beyond what the app's own trait impl already provides.

Consequences

logic's crate-type needs to list both cdylib (the artifact the dev path loads) and rlib (so the native host can depend on it as an ordinary crate) — not a new risk: the hot-lib-reloader draft already uses the equivalent dual declaration (["rlib", "dylib"]) for the same reason, one level native rather than wasm. Not built on any draft.
