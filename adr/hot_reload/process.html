Domain 4

Process split

wasm alone can't safely recover if the wasmtime-hosting code itself hangs or crashes — only a process boundary can, not a thread. A framework-controlled subprocess is the one piece of this record that isn't built yet.

D4.1

A framework-controlled subprocess hosts wasmtime, not the outer host process directly

accepted

The process the user launches owns the terminal and never runs wasmtime itself. It spawns a small, framework-authored child process; that child loads and calls into the app's compiled logic module.

Alternatives considered
  • Run wasmtime in-process, synchronously on the render loop's own thread — what every draft built so far actually does. Simplest, but every guest call blocks rendering and input for its duration, and a guest trap or a harness hang has no isolation from the host process beyond the sandbox itself.
  • Run wasmtime on its own background thread of the same process — removes the blocking problem above, and removes the IPC layer entirely. Logging is no longer a reason to prefer a subprocess over this, now that Domain 6's shared tagged file exists — a thread can write to it with exactly the same discipline a separate process can. Where it still falls short: a thread that hangs can't be safely killed and recovered, for the same reason D5.1 already rules out TerminateThread-class operations for a single call — only the whole process can be torn down cleanly, taking the render loop with it. And a hard crash anywhere on that thread, including inside wasmtime's own native runtime code (trusted host code the wasm sandbox doesn't cover), takes the whole process down regardless.
Reasoning

Logging doesn't motivate this split — conceded directly, not hedged: once app and framework logs both land in one shared, tagged file (Domain 6), a thread writes to it exactly as safely as a separate process does; being in a different OS process buys nothing extra there. What a thread genuinely cannot provide is safe kill-and-recover: a stuck or corrupted thread can't be terminated without risking the same heap/lock corruption D5.1 already rules out, and a hard crash in trusted host code sharing that thread's address space — wasmtime's own runtime, not the sandboxed guest — takes the whole process down with it regardless. A separate process is the only thing that contains either failure without also killing the render loop.

Consequences

This is the one decision in this record without a working draft behind it, and its justification narrowed on review: not built for logging's sake, but specifically for the crash/hang-containment property a background thread can't match. Every wasm-framework worktree built and live-tested so far runs wasmtime fully in-process, synchronously; moving it into a subprocess (or even just a background thread, which would still need D5.2's timeout without being able to act safely on it) is real remaining work, tracked in the SPEC.

D4.2

The IPC channel is a dedicated named pipe, reserved exclusively for the protocol

accepted

Host and the subprocess talk over a named pipe, carrying on_tick/handle_event/build_view requests and responses. The host creates the server end before spawning the child, under a name unique to that host process, and hands the child the name at spawn (argv or environment). The child connects. Nothing but the protocol is ever written to it. On Windows this is a named pipe; the Unix equivalent (a Unix domain socket or a FIFO) is not decided here.

Alternatives considered
  • The child's own stdin/stdout, via Stdio::piped() — what this decision originally said. It needs no platform-specific code, and the host sees end-of-file for free when the child exits. Rejected: it makes the child's stdout the protocol stream, so any stray println! or dbg! in the harness — hand-written code, exactly where such a slip happens — silently corrupts the protocol. It also forced D6.4 to rule out inherit_stdio() for that reason, tying the app's logging design to how the pipe was wired.
Reasoning

A dedicated channel removes a whole class of failure: the protocol stream is no longer a function of what the process happens to print. The child's own stdio can then be decided on its merits (D4.4) instead of being load-bearing. This keeps D6.1's four destinations separate by construction rather than by discipline.

Consequences

The cost is platform-specific code: the standard library has no portable named pipe, so Windows and Unix each need a backend (a crate that wraps both is an option). A named pipe also has a name another local process could try to connect to, so the host creates it first, accepts exactly one client, and where the platform allows refuses remote clients. A Unix socket file outlives a crash and needs cleaning up. Child death is still detected for free — the host sees the pipe close — and the byte-stream nature is unchanged, so messages still need framing. Waiting for the child to connect has no built-in timeout; see D5.2.

D4.3

Rendering and terminal ownership stay in the outer host, even with a subprocess in the picture

accepted

Adding a subprocess doesn't change D2.3: the subprocess has no TTY, renders nothing, and only ever relays data the outer host turns into terminal output.

Reasoning

Stated explicitly because it would be easy to assume "the subprocess is where the app runs" implies "the subprocess is where the app is drawn." It doesn't — the subprocess's only job is hosting wasmtime and relaying calls over the IPC channel.

D4.4

The subprocess's stdin is null; its stdout and stderr are piped to the host and logged

accepted

The child's stdin is set to null at spawn, so it can never read keys the host's input reader owns. Its stdout and stderr are piped to the host, which reads them line by line and writes each line to the shared log through the framework logger (D6.3), tagged as the child's: stdout at info, stderr at debug. The harness also installs a panic hook that logs through the framework logger, so a panic is recorded at its own level rather than as stderr text.

Alternatives considered
  • Leave them inherited — the default when stdio isn't piped. The child would share the host's terminal: a stray println! would draw over the TUI (the bug D6.2 already documents), and an inherited stdin would let the child read keystrokes the host's input reader is meant to own.
  • Set stdout and stderr to null — what this decision originally said. Every byte reaching the log file then goes through one writer discipline, but whatever the process prints outside the logger is lost: a stray println! or dbg!, and crash messages the runtime prints itself (an abort, a stack overflow), which a panic hook cannot catch. Rejected: losing that output costs more than relaying it.
  • Point stdout/stderr at the log file — keeps the same output for free, but those writes bypass the lock D6.3 requires every writer to hold, so a line could interleave with another process's.
Reasoning

The pipes are neither the terminal nor the IPC channel, so D6.1's destinations stay separate; relaying through the host keeps D6.3's discipline, since the host turns each line into one locked write. stderr carries dbg!, eprintln! and the runtime's own messages alike, with nothing to tell them apart, so it is logged as a whole at debug.

Consequences

The host runs two reader threads per child. Output from an abort or a fault is captured too, so a child that dies that way still leaves its last words in the log. Relayed lines travel separately from the child's own logger lines, so their order relative to each other is not guaranteed.
