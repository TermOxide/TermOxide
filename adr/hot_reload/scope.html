Domain 1

Scope of the hot-reload system

What "hot reload" means here, who it's for, and the one threat-model call that every later domain in this record depends on.

D1.1

Hot reload means the app author's dev loop, not a production distribution mechanism

accepted

The target is: edit logic, save, and see the change in the already-running terminal without restarting the process, and — as long as the state type's shape is unchanged — without losing in-memory state (D3.7). This is deliberately not a claim about speed — reload latency is dominated by cargo build's own compile time, which is not sub-second. What's being delivered is "you don't lose your running app and its state," not "this is fast." It is also not a distribution mechanism: not a way to package and ship a finished app to someone else's machine, and not an answer to "how do users install extensions" — this framework builds TUI apps from scratch; it isn't a store or a runtime for apps that already exist.

Alternatives considered
  • Build hot-reload as the foundation of a distribution/installation system — e.g. so a finished app could later be packaged and shipped to someone else's machine as a versioned, signed artifact, the way an extension marketplace would need.
Reasoning

Every domain in this record — the transport, the ABI, the process split, hang protection — is sized for "the app author, iterating on their own machine." Distribution is a different problem with a different threat model (see D1.2) and a different cost structure; conflating the two would have made every decision here more conservative than the dev loop actually needs.

Consequences

Reload latency is bounded by cargo build's own compile time, not by anything this design controls — a small incremental rebuild of just the logic crate is typically a few seconds with dependencies already warm, but it is not sub-second, and as of this record nothing times it out at all in the worst case (D5.7). Do not advertise a specific latency number anywhere downstream of this decision.

D1.2

Threat model is local and trust-at-download, not multi-tenant sandboxing

accepted

The person running the host process and the person who wrote logic are, in the cases this design optimizes for, either the same person or someone the user chose to download code from. This is not a design for running arbitrary untrusted code from strangers on shared infrastructure.

Alternatives considered
  • Capability-sandbox every app by default, the way a remote multi-tenant code-execution platform would.
Reasoning

This is exactly the trust model a lot of shipped local extension ecosystems already run under — Neovim plugins, tmux plugins, even cargo's own build scripts and proc-macros all execute arbitrary native code on every build, no sandbox, no prompt. Choosing to run an app is the consent boundary; running it doesn't need to re-litigate that boundary internally.

What this doesn't mean: an app still shouldn't be able to take the whole host process down by accident. Protecting against a buggy-but-not-malicious app (Domain 5) is a live goal. Protecting against an app author who is actively trying to do harm is not.

Consequences

This is the decision every capability call in Domain 7 reduces to. It is also why crash/hang containment (Domain 5) is framed as "don't let an honest bug take down the host," not "don't let a malicious payload escape a sandbox."

D1.3

Not restricting developer creativity is a first-class goal, not a nice-to-have

accepted

Filesystem, network, and stdio access for the app author are treated as things to preserve, not things the sandbox exists to take away. Where a decision elsewhere in this record (wasm, a subprocess boundary) could be read as restricting the app author, it is re-derived in Domain 7 to confirm it doesn't, before being accepted.

Reasoning

The transport chosen in D2.1 happens to come with a sandbox by default. That sandbox's capability restrictions are opt-in from the framework's side (D7.1), not an inherent limitation — the properties that actually motivated the transport choice (hang protection, crash containment, portability) hold independently of how permissively capabilities are configured.

D1.4

Backend-agnosticism, multithreading, and async events are framework goals this record doesn't block

deferred

The framework is meant to be backend-agnostic (ratatui, raw crossterm, or another renderer, chosen by feature flag), multithreadable, and able to drive async or multi-threaded event handling. None of that is built by this record — but nothing decided here forecloses it either. See Domain 10 for where each currently stands.

Reasoning

The app-author boundary settled on in Domain 3 — guest computes data, host renders (D2.3) — is what keeps these open. A guest that called a specific rendering backend's API directly would have hard-wired every app to that backend; a guest that owned its own event loop would have made "run the host loop on multiple threads" a much bigger rewrite. Neither happened.

Consequences

The styling ADR's own D1.4 — "hot reload means whole-application dev reload, not a style watcher" — is a forward reference to this record. A style edit is just a logic edit like any other; it goes through the same rebuild-and-swap this whole document specifies, not a separate style-specific hot-patch path.

That entry also estimates "a rebuild on the order of a second." Treat that specific number as unverified against this record's own finding (D1.1) that reload latency is cargo build-dominated and not sub-second — the style ADR's actual requirement (no dedicated style-file watcher) holds regardless of the exact number, but the number itself shouldn't be repeated as a guarantee.

D1.5

Release builds compile logic directly into the host binary; none of this record's machinery ships

accepted

A finished, distributed app links logic natively into one binary alongside the host/render loop — no wasmtime, no subprocess, no IPC, no fuel/epoch, no postcard marshaling. Everything this record describes exists to answer "how do I see my edit without losing state or restarting"; a shipped binary is never edited again, so there's nothing left to protect against mid-reload.

Alternatives considered
  • Ship the same wasm+subprocess architecture in release too — one code path throughout, but it pays sandbox indirection, a runtime dependency on wasmtime, a separate .wasm artifact to distribute, and the whole generation-management apparatus (Domain 5) for a program that will only ever have one generation, forever.
Reasoning

Follows directly from D1.1 — hot reload is explicitly the dev loop, not a distribution mechanism. Shipping its machinery anyway would quietly reintroduce the production cost this record otherwise avoids, with no corresponding benefit once there's no reload happening.

Consequences

Worth flagging as a separate, legitimate question rather than folding it in here: whether the framework wants crash isolation in production, independent of hot-reload — so a bug in the app's own code can't take the whole terminal session down. None of Domain 5 is scoped for that; it's entirely about reload generations. If that's ever wanted, it needs its own decision, not a reuse of this one. See D3.6 for the mechanism that makes switching between the two paths free for the app author.
