Domain 9

Static analysis & tooling

What the wasm ecosystem could buy back against its own runtime cost — most of it already sitting in the dependency tree, unused.

D9.1

wasm-tools/wasmparser introspection validates a rebuilt module before loading

deferred

Before Instance::new is even attempted, inspect the freshly built module's import/export table directly — catch a malformed or unexpected module with a purpose-built error message, enforce a size or import-allowlist budget in CI, or lint a logic crate that tries to import something host never exposes.

Reasoning

wasmparser, wasm-compose, and wit-parser are already transitive dependencies of wasmtime — visible compiling in every build log across every wasm draft in this project, without ever being asked for directly. Adopting this costs nothing in new dependencies, only integration work. No comparable tooling exists for introspecting a native dylib's export table with the same ergonomics or standardization.

D9.2

Component Model / WIT is a future option, not the v1 wire format

deferred

Defining the on_tick/handle_event/build_view interface as a .wit file and generating bindings with wit-bindgen, instead of the hand-rolled postcard + fixed-capacity-buffer scheme in Domain 3, was considered and set aside for v1.

Reasoning

The upside is real: richer types (strings, records, variants, lists) would cross the boundary natively instead of through a manually-sized buffer, and a component-model guest isn't necessarily Rust-only — any language with a component target (C, TinyGo, componentize-py) could implement the same interface. Also not a new dependency: wit-parser and wasm-compose are already pulled in transitively by wasmtime, same as D9.1.

Set aside because it's a real rewrite of the abi crate, not an incremental addition — the right call once cross-language guests or a stronger interface-versioning story become actual requirements, not before.
