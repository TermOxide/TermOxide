Domain 8

State persistence

Surviving a full host restart, not just a reload — and why it costs nothing extra on top of Domain 3's encoding.

D8.1

Persistence is opt-in, layered on the base transport, never a separate design

accepted

A reload alone never loses app state — state lives in host for the whole process lifetime, untouched by swapping logic. Persistence exists only for the case a reload can't cover: restarting the host process itself, which happens when non-logic code changes — and, in a release build, for keeping the app's state between runs (D1.5). The app's main opts in with run_app!(persistent), which the person running it can override (D8.7), and TERMOXIDE_FRESH=1 starts one run from a clean state, which then replaces the trace.

Reasoning

Confirmed live across every transport drafted: killing the host process outright mid-session and starting a fresh one restores exactly where the previous run left off, under a new pid, without any change to the app's own code.

D8.2

For wasm and dylib, persistence adds no new encoding step

accepted

A persistent run reads the same opaque byte blob (D3.3) from its state trace on startup and writes it there after every recorded change (D8.4). No new trait bound, no app-side derive beyond what D3.2 already required.

Alternatives considered
  • hot-lib-reloader's persistence story, for comparison — there, host holds a live, un-encoded, real Rust S value in-process (that's the whole point of that transport). Persistence is the first point encoding is needed at all, so it does need a new Serialize + DeserializeOwned bound and an app-side derive that wasn't otherwise required.
Reasoning

Both wasm and dylib already pay the "state must be bytes" cost on every single call, for the live reload boundary itself (D3.2) — for a completely different reason than persistence. Persistence just writes those same bytes to a file instead of into guest memory. There's no new encoding to add — but the snapshot must carry the state-schema fingerprint from D3.7, because a file written by an older build outlives the process that wrote it and is exactly where a changed state type gets misread.

D8.3

The snapshot path is fixed, not pid-keyed

accepted

One path per app, deterministic, not derived from the running process's pid: state.bin in termoxide/<app>/, next to the logs (D6.5).

Reasoning

The entire point is finding the file across a pid change — a freshly started host (a new pid, after the restart persistence exists to survive) has to be able to locate what the previous process wrote. A pid-keyed path would defeat the purpose.

D8.4

A run keeps a trace of every recorded change, not one snapshot

accepted

state.bin starts with the line termoxide state trace 1 and a header naming the app's manifest directory, then holds one postcard entry { at, state } — milliseconds since the Unix epoch, the state bytes — per change of a recorded signal (D3.11). Each run starts a new trace with the state the app started from, written beside the last run's and renamed over it, then appends to it; the next run starts from the last entry. Each trace covers one run, however long.

Alternatives considered
  • One snapshot, replaced on every change — what was built first. Rejected: when a state makes the app crash, the snapshot shows where it ended up, not how it got there.
  • The last N changes, or a size cap — bounded, but a long run's beginning is lost, and one run's trace is already bounded by how long the developer runs it.
Reasoning

A trace answers the question persistence raises once a state misbehaves: what happened before. Recording only recorded signals keeps it to the changes a developer cares about, so a tick count doesn't add ten entries a second.

Consequences

An entry cut short by a host killed while appending is skipped when reading. The first entry of a run is written beside the old trace and renamed over it, so a host killed then leaves the previous trace whole. Every entry holds the state's fingerprint (D3.7), so a trace can span a change of state type.

D8.5

A trace that might crash the app, or can't be read, is set aside, never loaded again

accepted

When the app stops for crashing too often (D5.9), its trace is renamed state.bin.crashed, so the next run doesn't start from the state that crashed it. A file that isn't a trace, or a trace whose last state fails to decode, is renamed state.bin.unreadable and the app starts afresh. A trace saved by another state type resets the app (D3.7), and the run's own trace replaces it.

Alternatives considered
  • Delete a bad trace — loses what would explain the crash.
  • Keep starting from it — a state that crashes the app on start would stop it again on every run.
  • Keep the old trace aside when the state type changes too — not chosen: going back to the old type is rare, and the reset is already what a reload does.
D8.6

termoxide dump prints a trace, decoded by the app's own component, found from the trace or from the app's crate

accepted

termoxide dump [<path>] [--bin <name>] [--crashed | --unreadable] [--manifest <Cargo.toml>] builds the app's guest and asks it to Describe each entry. It prints each entry's time, its state type's fingerprint — highlighted where it changed from the previous entry, in color on a terminal, in words elsewhere — and the app as JSON. <path>, . by default, is a trace, whose header names the crate to build, or the app's crate folder, which names the trace: <app> is the executable's name from cargo metadata — its only [[bin]], or the package's name when it runs through termoxide run — and the trace its state.bin, or with --crashed / --unreadable the one set aside (D8.5). --manifest names the crate when a trace's header points where it no longer is.

Alternatives considered
  • A trace path only — what was built first. The developer has to know where the platform keeps termoxide/<app>/, when the crate they're working in already says.
  • An environment variable on the app's own executable that prints a trace instead of running the app — built first, removed: one tool reads any trace, and the executable only runs the app.
  • Pass the app's manifest or its .wasm every time — nothing new in the trace, but the developer has to know which build wrote it.
  • Put one fingerprint in the header — a trace can span a change of state type, and the host would have to take the state bytes apart.
Reasoning

Only the guest can decode the app's state (D3.3), so a reader needs the app's component; naming its crate in the trace makes the trace enough. The guest returns the fingerprint with the JSON, so the state stays opaque to everything else.

Consequences

A crate with several bins doesn't say which one wrote the trace: it needs --bin, as with Cargo. When state.bin is missing and a trace set aside exists, the error names it. Given a crate folder, the tool reads the app's own trace whichever build wrote it, release included (D1.5).

D8.7

Whether a run persists is read at run time: environment, then config file, then the app's default

accepted

First match wins: TERMOXIDE_PERSIST=0 or 1; then persist = true or false in config.toml in termoxide/<app>/, next to the trace and the logs (D8.3); then the app's default, run_app!(persistent) or persistent = true under [package.metadata.termoxide] for an app run through termoxide run (D3.12). The same order holds in both profiles. TERMOXIDE_FRESH=1 stays environment-only. The app's argv is never read.

Alternatives considered
  • The app's default only, in run_app! or the manifest — rejected: someone who downloaded a release build has neither, and couldn't change it without recompiling.
  • Flags on the app's own binary, such as --persist — rejected: argv belongs to the app, and a framework flag can collide with its own CLI or take an argument it expected.
  • Reserved flags, such as --termoxide-persist, removed before the app sees argv — works, but surprises an app that parses its own arguments.
  • The TERMOXIDE_HOT_RELOAD_* names the variables had at first — renamed: they now apply to a release build, where nothing hot reloads.
Reasoning

A config file is what a user who downloaded an app expects to edit, and lives where the app's other files already are. The environment comes first because it's the narrower choice: one run, one shell, without touching what every run reads.

Consequences

FRESH has no config key, which would start every run fresh. The termoxide CLI owns its own argv, so its --persist, --no-persist and --fresh set the variables for the run and come first.
