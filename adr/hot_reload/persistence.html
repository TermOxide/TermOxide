Domain 8

State persistence

Surviving a full host restart, not just a reload — and why it costs nothing extra on top of Domain 3's encoding.

D8.1

Persistence is opt-in, layered on the base transport, never a separate design

accepted

A reload alone never loses app state — state lives in host for the whole process lifetime, untouched by swapping logic. Persistence exists only for the case a reload can't cover: restarting the host process itself, which happens when non-logic code changes.

Reasoning

Confirmed live across every transport drafted: killing the host process outright mid-session and starting a fresh one restores exactly where the previous run left off, under a new pid, without any change to the app's own code.

D8.2

For wasm and dylib, persistence adds no new encoding step

accepted

run_persistent reads the same opaque byte blob (D3.3) from a snapshot file on startup and writes it back after every state change. No new trait bound, no app-side derive beyond what D3.2 already required.

Alternatives considered
  • hot-lib-reloader's persistence story, for comparison — there, host holds a live, un-encoded, real Rust S value in-process (that's the whole point of that transport). Persistence is the first point encoding is needed at all, so it does need a new Serialize + DeserializeOwned bound and an app-side derive that wasn't otherwise required.
Reasoning

Both wasm and dylib already pay the "state must be bytes" cost on every single call, for the live reload boundary itself (D3.2) — for a completely different reason than persistence. Persistence just writes those same bytes to a file instead of into guest memory. There's no new encoding to add — but the snapshot must carry the state-schema fingerprint from D3.7, because a file written by an older build outlives the process that wrote it and is exactly where a changed state type gets misread.

D8.3

The snapshot path is fixed, not pid-keyed

accepted

One path per app, deterministic, not derived from the running process's pid.

Reasoning

The entire point is finding the file across a pid change — a freshly started host (a new pid, after the restart persistence exists to survive) has to be able to locate what the previous process wrote. A pid-keyed path would defeat the purpose.
