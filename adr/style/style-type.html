Domain 2

The Style type and how it is authored

One property table covering paint and layout, partial by construction, merged by argument order.

D2.1

One Style type holds both paint and layout properties

accepted

A single property table contains fg, bg, bold, border alongside padding, width, flex_grow, display. Every property carries a static classification: Paint, Layout, or Both.

Alternatives considered
  • Split systems — layout as typed props on the node, style as paint-only. Simpler to implement, and roughly what ratatui-adjacent designs do.
Reasoning

Users think of padding and background as one concern, and some properties genuinely are both: padding moves the box and changes the area bg fills. A split also breaks slot-based override (D4.3) the moment anyone wants to restyle spacing.

Consequences

The classification is what drives the two dirty bits in D3.2: the layout solver only wakes for properties that can move a rectangle. Any layout-affecting input that lives outside Style would bypass that machinery — which is why text_wrap is a style property (D8.7).

D2.2

Every property is tri-state: Unset / Inherit / Value

accepted

Style is partial by construction. A property is either unspecified, explicitly inheriting from the parent, or carrying a value.

Alternatives considered
  • Option<T> per property — partial, but no way to say “explicitly inherit”.
  • Plain T with a Default impl — simplest, smallest.
Reasoning

Plain T makes override unimplementable: you cannot distinguish “the caller didn't mention bg” from “the caller explicitly set bg to the default value”, so merge has no way to know which side wins. This is the single most consequential representation decision in the system.

Inherit is separate from Unset because inheritance is opt-out for paint properties and opt-in for others — the CSS inherit keyword applied to a non-inherited property.

D2.3

Merge is last-write-wins per property, in argument order

accepted

a.merge(b) takes every set property from b and leaves a's value wherever b is Unset. There is no specificity and no !important.

Alternatives considered
  • CSS specificity — weights by selector shape.
  • Source-order cascade with an escalation escape hatch.
Reasoning

This is the one idea worth importing from StyleX, and it survives translation to Rust intact. Precedence is visible at the call site as argument order; there is nothing to escalate against, so no !important is needed. CSS specificity exists to arbitrate between selectors, and there are no selectors here.

Consequences

Component authors write merge chains explicitly — see D3.5. Reading precedence is reading Rust, not consulting a specificity table.

D2.4

Two authoring forms: the style! macro and the builder

accepted

style! { bg: Surface, pad_x: 2, min_width: 20 } is the idiomatic literal form and is const-evaluable when all values are literals. The builder (Style::new().bg(..)) is the runtime and composition API.

Alternatives considered
  • Builder only — no macro, no new syntax to learn or maintain.
  • Macro only — one way to author, but no runtime construction.
Reasoning

The builder is non-negotiable because D1.2 requires applications to build styles from config at runtime. The macro is worth its cost because it reads like the CSS people already know and hoists to a constant, which is the second useful idea from StyleX: module-level style constants merged in order at the use site.

Consequences

StyleX's atomic class compilation is explicitly rejected. It exists to deduplicate a stylesheet shipped over a network and to exploit the browser's CSSOM. There is no network and no CSSOM here. Take the merge semantics; leave the compiler.

D2.5

No flattened shorthand props on primitives

accepted

<Box style={s}> is the only way to style a node. There is no <Box bg=Blue padding=1>.

Alternatives considered
  • Shorthand on primitives only, with a documented rule for what <Box bg=Blue style={s}> means when s also sets bg.
  • Shorthand everywhere, including components.
Reasoning

Named style slots (D4.3) mean a component may expose several styleable regions. Flattening would require header_bg, header_padding, row_fg — the cross product of slots and properties. Since the style object must be the unit of transfer anyway, shorthand would be a second, inconsistent system layered on top.

The cost is real: the 80% case is more verbose to write. The style! macro is what makes that acceptable.
