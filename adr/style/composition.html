Domain 4

Inheritance, states and composition

How styles flow down the tree, how a third-party component gets restyled, and how interactive state is expressed without pseudo-classes.

D4.1

Paint properties inherit down the tree

accepted

Colour and text attributes inherit like CSS color. Layout properties do not.

Alternatives considered
  • No inheritance — every node states everything explicitly.
  • Inheritance only via theme context, never structurally.
Reasoning

Setting a panel's colour and having its text follow is the single most common styling gesture in a terminal UI. Without inheritance it requires threading colour through every leaf.

D4.2

Inheritance is shared by pointer, not copied down

accepted

Each node holds an Rc<Inherited>. A node that overrides nothing shares its parent's record; a node that overrides something allocates a new one. Paint reads own_style overlaid on inherited.

Alternatives considered
  • Resolve eagerly — copy inherited values into each node during a top-down pass.
  • Resolve lazily at paint by walking up the parent chain per property.
Reasoning

Copying makes a parent's fg change an O(subtree) invalidation walk, which destroys the targeted-write property of D3.1. Walking up at paint time turns every property read into a chain traversal.

Sharing by pointer means a parent change swaps one Rc and every sharing descendant observes it with zero per-node work. This is essentially the computed-style sharing browsers use.

Consequences

The cells still have to be repainted — the screen genuinely changed. That is what subtree_paint_dirty is for, and it costs one bit on one ancestor.

D4.3

Named style slots are a component's public styling contract

accepted

A component exposes style, header_style, row_style, selected_row_style and so on as ordinary typed props. A theme context provider covers cross-cutting defaults so that “everything uses my accent” does not require passing forty props.

Alternatives considered
  • A single style prop. Reaches the outer box only; a component's internals stay unreachable and users fork the crate.
  • A ::part()-style escape hatch — terse, reaches anything.
Reasoning

Third-party restyling is a hard requirement: a shipped DataTable must be restyleable without patching the crate. It is also the historical origin of CSS specificity, !important, and StyleX's entire merge-order design — so it needs an answer, not an omission.

::part() reintroduces string matching, runtime failure modes, and the parser deleted in D1.1. Slots are verbose but typed, discoverable through rustdoc, and checked at compile time.

Consequences

Verbosity is the accepted cost. It is also why shorthand props were rejected (D2.5) — flattening does not survive contact with slots.

D4.4

Interactive state is signals, not pseudo-classes

accepted

The framework maintains per-node hovered, focused, active, disabled flags and exposes them as signals. There is no pseudo-class matching engine.

Alternatives considered
  • Pseudo-class selectors as the primary model, CSS-style.
Reasoning

CSS invented :hover because there was no cheap way to run code on every mouse move. With fine-grained reactivity that constraint does not exist — if hovered() { .. } is just a closure re-running, which is exactly the mechanism from D3.1.

This was originally specified alongside theme-file state selectors. When theming moved to the application layer (D1.2), the selector half became unnecessary — an application's own resolver can express state however it likes.

D4.5

Hover styles require a keyboard-focus equivalent; the framework lints

accepted

Using a hover style without a corresponding focus style is a lint, not an error.

Alternatives considered
  • Automatic fallback — a hover style implicitly applies on focus.
  • Silence — accept that hover sometimes does nothing.
Reasoning

Hover depends on mouse reporting, which is exactly what the SSH and multiplexer environments in the degradation matrix make unreliable. A UI whose only affordance is a hover style becomes invisible in those environments.

Automatic fallback was rejected because hover and focus are not always the same intent, and silent substitution produces surprising visuals. A lint puts the decision in front of the developer without taking it for them.
