Domain 10

The pipeline and the renderer

Where the styling layer actually lives — the original question — and what it implies about building on ratatui.

COMPILE TIME
  style!{…}  ──▶ const Style   (partial, tri-state)

ONCE PER TREE BUILD
  component fn ──▶ nodes in slotmap arena
                   each holds: static Style │ reactive closure

PER CHANGE          (targeted write — no tree rebuild)
  ① merge      slot default ◀ theme ctx ◀ passed style ◀ state
               ──▶ node.target_style          [D2.3, D3.5]
  ② inherit    node.inherited: Rc<Inherited>    [D4.2]

PER FRAME
  ③ animate    target ──interpolate──▶ presented   [D9.1]
  ④ layout     presented[Layout|Both] ──▶ taffy ──▶ integer edges
  ⑤ paint      presented[Paint|Both] + TerminalProfile ──▶ cells
  ⑥ diff       cell buffer diff ──▶ CUP + SGR bytes
D10.1

The styling layer is not a separate compilation stage

accepted

Styles are values resolved at stages ① and ② and consumed at ④ and ⑤. There is no separate compilation pass and no intermediate artifact analogous to a stylesheet.

Alternatives considered
  • StyleX-style precompilation — compile styles to atomic classes, attach them to nodes before rendering.
  • Resolution during node-tree construction, baking final values into nodes.
Reasoning

Atomic-class compilation exists to deduplicate a stylesheet shipped over a network and to exploit a CSSOM that already implements the cascade. Neither exists here — there is no wire format and the renderer is owned end to end.

Baking values at construction time is incompatible with D3.1, which requires the style to be rewritable without rebuilding the node.

Consequences

This answers the original framing directly: styling is neither a separate compiler nor part of node-tree compilation. It is a value written into a live node by an effect.

D10.2

A custom renderer rather than building on ratatui

accepted

The framework owns the cell grid, the frame diff and the byte stream.

Alternatives considered
  • Build on ratatui, which already provides a cell grid, frame diffing and absolute positioning.
Reasoning

The payoff is not obtaining a cell grid — ratatui has one, and arguing otherwise argues for something available for free. The payoff is ownership of four things: the width oracle injected into every consuming path (D8.3); simultaneous control of the cell model and the outgoing bytes, which mode 2027 negotiation and OSC 66 emission both require; per-cell provenance recording how a width was determined, so suspect cells can force full-line repaints; and the ability to re-derive layout when capabilities change (D8.5).

This session's decisions compound that: an owned dirty-bit classification, two-pass layered layout, paint-time symbolic colour lowering, and Rc-shared inherited style.

Consequences

Caveat. The claims about where ratatui computes width were reasoned from its general architecture, not verified against source (D8.9). The conclusion holds on the other four grounds; the ratatui-specific argument should be checked before it is used publicly.

D10.3

Three invalidation classes, not one

accepted

Node-local paint, node-local layout (plus the subtree paint bit), and global relayout on profile generation change.

Alternatives considered
  • One global dirty flag and a full redraw each frame.
  • Node-local only, with no global entry point.
Reasoning

A full redraw each frame would work at terminal scale and would discard the entire rationale for the node-level reactivity in D3.1. Node-local-only leaves nowhere to put a profile change, which is the one genuinely global event in the system.
