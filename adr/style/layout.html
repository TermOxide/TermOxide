Domain 5

Layout model, units and the box model

Where CSS semantics are adopted, where they are narrowed, and the three places the terminal has a better answer than the web does.

D5.1

Flexbox family, via Taffy's low-level API, over an owned node tree

accepted

Taffy supplies the layout algorithms. The framework keeps its own node tree and drives Taffy through its low-level interface.

Alternatives considered
  • Hand-rolled flexbox. Full control, no dependency.
  • Ratatui-style constraint layout. Simpler, terminal-native, less expressive.
  • Taffy's high-level tree API — let Taffy own the nodes.
Reasoning

Taffy implements Block, Flexbox and CSS Grid faithfully to the specifications, so MDN documentation transfers directly — a real benefit given the framework's stated goal of resembling web frameworks. Taffy's own guidance recommends the low-level API for embedders that already have a node tree, which is the case here (D3.4).

Consequences

Taffy does not implement text layout. Leaf measurement is supplied by the embedder, and in a terminal that is the genuinely hard part — grapheme segmentation, wide characters, emoji width disagreement. Taffy solves perhaps 60% of the layout problem, not 95%. See Domain 8.

D5.2

Four units: Cells, Percent, Fr, Auto

accepted

Nothing else. min_* and max_* exist as properties taking these units.

Alternatives considered
  • The CSS unit vocabulary — px, em, rem, vh, ch.
  • calc() and clamp() as unit expressions.
Reasoning

There is no font size in a terminal, so most of CSS's unit vocabulary is meaningless; each one adopted would be a permanent API whose behaviour must be defined and defended. calc() and clamp() exist because CSS cannot compute — Rust can, so an application does the arithmetic and passes a value.

min_*/max_* are properties rather than unit expressions and are retained: flexbox is not usable without them, since flex_grow with no ceiling lets one long label consume an entire row.

D5.3

padding: 1 means one cell, with no aspect compensation

accepted

Units are literal. A cell is roughly twice as tall as it is wide, and the framework does not hide that. pad_x and pad_y shorthands exist; the 2:1 convention lives in the widget library's defaults, not in the layout engine.

Alternatives considered
  • Automatic compensation — padding: 1 resolves to two columns and one row so it looks symmetric.
  • A global aspect knob the application sets once.
Reasoning

Cell aspect ratio is font- and terminal-dependent, not reliably 2:1, so any compensation factor is a guess baked into layout. It also breaks the moment a user mixes padding=1 with padding_left=3 and gets two different unit meanings in one declaration.

Convention in the component layer; honesty in the layout layer.

D5.4

Children tile their parent exactly; sibling sizes may differ by one cell

accepted

Round absolute edges to integers, then derive each child's size as right_edge − left_edge. Rounding errors cannot accumulate and children always fill the parent exactly.

Alternatives considered
  • Round sizes independently and accept gaps or overflow — three children at 33.3% of 80 cells give 78 or 81.
  • Use Taffy's built-in rounding unmodified.
Reasoning

A one-pixel gap in a GUI is a hairline. A one-cell gap in a terminal is a hole. Bevy's history is the cautionary tale: they disabled Taffy's rounding, added ad-hoc replacements, and the visible narrow lines in their UI were gaps caused by coordinate rounding errors — the hacks were eventually removed.

Taffy exposes rounding as a separable pass (RoundTree / round_layout), so its algorithms can be kept while the rounding rule is replaced with a cell-appropriate one.

Consequences

Unverified: Taffy's exact round_layout algorithm was not read. It may already round absolute coordinates, in which case the default suffices. Read the source before writing a replacement.

D5.5

border-box only, and not configurable

accepted

width: 20 means twenty cells on screen, inclusive of padding and border.

Alternatives considered
  • Support both, defaulting to border-box.
  • CSS's default, content-box.
Reasoning

content-box is so widely regretted that * { box-sizing: border-box } appears in essentially every CSS reset written. There is no backward-compatibility obligation here, and offering both means every component author must consider both.

Removing the option removes a class of bug rather than a capability.

D5.6

A border is exactly one cell; style is per-box, sides toggle presence

accepted

There is no border_width. What varies is the glyph set — single, double, rounded, thick, ASCII, none — chosen per box. Individual sides may be turned on or off.

Alternatives considered
  • Per-side border styles, resolving corners on a best-effort basis.
  • Per-side styles with an error on unrepresentable junctions.
Reasoning

A border cannot be thicker than a cell, so width is not a meaningful axis. Per-side styles fail on a character-set constraint rather than an implementation one: where a double top meets a single left, the Unicode box-drawing block may contain no glyph for that junction. Best-effort resolution produces silently wrong corners; erroring produces a runtime failure for something that should not have been expressible.

D5.7

overflow: hidden is the default, implemented as clip-at-paint

accepted

Content is clipped to the node's rectangle. visible does not exist. Scrolling is deferred, but clipping must be applied during paint, never by clamping children during layout.

Alternatives considered
  • CSS's default, visible.
  • Clamp at layout — tell the solver children cannot exceed the parent.
  • Ship scroll in v1.
Reasoning

visible is actively dangerous without a compositor: overflowing content paints over siblings in whatever order paint happened to run, which is a debugging nightmare with no z-buffer to arbitrate.

Clamping at layout produces output identical to clipping today and permanently forecloses scrolling, because the scrollable extent is precisely the amount by which a child's natural size exceeds the viewport. Lay children out at natural size, clip at paint, and adding scroll later is an offset plus input handling.

Consequences

Deferred, not foreclosed. TUI applications are overwhelmingly lists; expect scroll in v2. The one line of discipline is: natural sizes in the solver, clipping in the painter.
