Domain 8

Text measurement and the width oracle

The hardest correctness problem in the system, and the one Taffy does not solve. Folded in from a dedicated research session.

ProvenanceThis domain consolidates a separate research session on terminal display width. Its unverified items are carried through as unverified rather than promoted to decided facts — see D8.9.

D8.1

Display width is an agreement, not a property of a string

accepted

The framework treats width as negotiated state, not as a pure function of text.

Alternatives considered
  • Treat unicode-width as ground truth and move on.
Reasoning

Four parties can disagree: the Unicode version each side compiled against, the measurement model (per-codepoint versus per-grapheme-cluster — 👩‍🌾 measures 4 or 2 depending), per-terminal quirks around ambiguous width and variation selectors, and multiplexers, which are themselves emulators with their own width logic sitting in the middle.

Survey evidence: one ZWJ cluster reported as 2, 4, 5 and 6 columns across terminals; ucs-detect across ~35 terminals found 23 distinct implementations of which codepoints are wide and 19 distinct implementations of ZWJ emoji width.

D8.2

A layered width oracle, not a width function

accepted

Cluster-aware table lookup as the default; CPR probing at startup for ground truth; DEC mode 2027 as an upgrade-only signal; OSC 66 behind a capability flag. Unmeasurable clusters are clamped to two cells or replaced with U+FFFD.

Alternatives considered
  • Static per-codepoint table (unicode-width) — wrong for exactly the content this project must handle.
  • Static cluster table only — correct in modern terminals, blind to legacy ones.
  • OSC 66 as the primary path — architecturally correct, but Kitty and Foot only as of the research date.
Reasoning

Each strategy has a different failure mode and none is sufficient alone. CPR probing is the only method that measures ground truth and the only one that sees through tmux, at the cost of a round-trip per probe. Mode 2027 is useful as an upgrade signal and useless as a downgrade signal — capable terminals frequently do not answer the query at all, so silence must never be read as a negative.

Clamping is evidence-backed rather than a shortcut: wcwidth 0.8.0 adopted a two-cell ceiling per grapheme cluster after measuring that grapheme-aware terminals rarely advance further.

Consequences

Rendering something known to corrupt the grid is worse than rendering a replacement character. Hostile input — Zalgo, long virama chains, standalone regional indicators — is substituted, not measured.

D8.3

The oracle is injected at every width-consuming site

accepted

A trait object reaches truncation, wrapping, cursor placement, alignment and mouse hit-testing. Layout and paint share one authority.

Alternatives considered
  • A free function called wherever width is needed.
  • Separate measurement per stage, each tuned to its needs.
Reasoning

If any call site reaches for unicode_width::UnicodeWidthStr::width directly, the layering is defeated silently. If layout and paint ever disagree, the result is the ghost-character corruption the whole system exists to prevent — and it will be intermittent and terminal-specific, the worst possible bug profile.

D8.4

Leaf measurement takes available space from day one

accepted

The measure signature accepts an available-space argument and returns min-content and max-content sizes, even while v1 ignores the argument.

Alternatives considered
  • A parameterless measure(&self) -> Size, changed when wrapping arrives.
Reasoning

Without wrapping, a text leaf is one row tall and its size depends on nothing. With wrapping, height depends on available width — which changes the signature at every leaf and every call site in the layout driver. Taffy's measure API already passes available space for this reason.

Flexbox additionally needs both min-content (widest unbreakable run) and max-content (the whole string) to resolve flex_grow, so one number was never enough.

D8.5

The profile is frozen at startup in v1, with a generation counter built now

deferred

Probe at startup, block until the calibration set completes, then freeze. Every cached measurement records the profile generation it was taken under; a stale generation forces remeasurement. A profile change triggers a global relayout.

Alternatives considered
  • Full mid-session re-measurement in v1 — handle tmux attach/detach and late protocol responses.
  • Freeze with no seam — simplest, but every cached-measurement site must be found later.
Reasoning

Disaggregate what a profile change invalidates: a colour-tier change needs a repaint only; mouse support changes nothing visual; only the width oracle invalidates measurements, and that fires rarely — at startup, or on reattach.

Rare plus globally-invalidating means the simplest implementation is correct: drop cached measurements, mark the root layout-dirty, relayout. On a tree bounded by a terminal's cell count that is sub-millisecond. The real question was never the algorithm but whether the architecture has somewhere to put the call, given that D3.1 made all invalidation node-local.

Consequences

The generation counter turns “invalidate everything” into a data comparison rather than control flow threaded through the tree. v1 limitation: tmux attach mid-session is unhandled, documented rather than lurking.

D8.6

Wrapping: Char in v1, approximate Word, UAX #14 in v2

deferred

text_wrap lives in Style and is Layout-classified. text_overflow is Paint-classified, since the box is already sized.

Alternatives considered
  • No wrapping in v1 at all.
  • Proper UAX #14 line breaking immediately.
  • Wrapping as a Text widget prop rather than a style property.
Reasoning

Char wrap is genuinely trivial given grapheme segmentation and the oracle, and it is correct for every script — merely ugly for prose. Word wrap by whitespace is ~50 lines but degenerates completely for CJK, which has no spaces and wraps at nearly any character; since arbitrary user text including CJK is a hard requirement, naive word wrap must be documented as approximate rather than presented as done.

Keeping it in Style follows from D2.1: a layout-affecting input outside the property table would bypass the classification and the dirty bits.

Consequences

Omitting wrapping entirely would mean no paragraphs, no help text, no multi-line errors and no log lines. Together with scroll, that is most of what TUI applications display.

D8.7

RTL and bidirectional text are out of scope for v1, and not foreclosed

deferred

The cell-writer API is indexed by position rather than assuming append order, so bidirectional reordering remains possible.

Alternatives considered
  • Design for bidi now.
  • Rule it out permanently and simplify accordingly.
Reasoning

Bidi is a large, self-contained problem that interacts with cursor placement, selection and hit testing as much as with rendering. Deferring it is reasonable; assuming left-to-right append order throughout the cell writer would make it unreachable, which is not.

D8.8

Absolute cursor positioning per run or per line

accepted

The renderer emits CUP rather than relative movement derived from a computed width.

Alternatives considered
  • Relative cursor movement, which is fewer bytes.
Reasoning

This is the bounded damage property: when a width guess is wrong, corruption stays in that cell instead of desynchronising the rest of the line and everything after it. Given that D8.1 establishes some guesses will be wrong, containing the blast radius matters more than byte count.

D8.9

Carried-forward unverified items

unverified

Four claims from the width research were reasoned or dated rather than confirmed, and are recorded as open.

Alternatives considered
  • Whether current unicode-width handles VS15/VS16 presentation selectors — the criticism found may predate recent releases.
  • Whether librio's cluster_width is published to crates.io or in-tree only.
  • Ratatui's current internals, including where and how it computes width — reasoned from general architecture, not read.
  • Ghostty's OSC 66 status, parse-only as of 1.3.0 (March 2026); may have advanced.
Reasoning

These are load-bearing for D10.2 in particular. The conclusion there holds on independent grounds, but the ratatui-specific argument should not be made in public until the source has been read.
