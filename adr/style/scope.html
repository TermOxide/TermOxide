Domain 1

Scope of the styling system

What the framework owns, what it deliberately hands back to the application developer, and the single decision that deleted the largest source of permanent complexity.

D1.1

The framework provides a styling type, not a styling language

accepted

There is no CSS/SCSS parser, no selector engine, no specificity rules, no cascade, and no string-addressable property namespace in the framework's public API. Styling is a Rust value.

Alternatives considered
  • Adopt a CSS subset. Familiar syntax; the path r3bl_tui and revue took.
  • SCSS-like DSL with nesting and variables.
  • Own TUI-specific language designed around cells rather than pixels.
Reasoning

Every text language obliges you to own a parser, an error-reporting story, a resolution order, and a runtime type-erasure boundary — permanently, across every version. That tax is only worth paying if someone who cannot recompile needs to write styles.

Once theme-file loading moved to the application layer (D1.2), nobody in that position remained. The requirement that justified the language disappeared, so the language did too.

Consequences

The original framing — “adopt the whole CSS spec or write my own styling language?” — resolves to neither. What remains is a typed property table with a defined merge operation.

Individual CSS semantics are still adopted or rejected case by case; see Domain 5. It is the syntax and the resolution machinery that are gone.

D1.2

Theme files belong to the application, not the framework

accepted

The framework guarantees that Style values can be constructed and composed at runtime. An application that wants user-editable themes writes its own config format and its own resolver, producing Style values it passes to component style props.

Alternatives considered
  • Framework-owned theme loading with a standard file format, selector matching and precedence rules.
  • No runtime theming at all — styles are compile-time constants only.
Reasoning

Framework-owned theming means the framework must arbitrate between a theme file and a component's own styles, which means precedence rules, which means a cascade — the thing D1.1 deleted. The second option fails a stated requirement.

Pushing resolution to the application keeps the framework's obligation to exactly one thing: Style must be ordinary constructible data.

Consequences

Style cannot be a macro-only or opaque type. It needs public fields or a full builder API, and a merge operation with documented semantics. See D2.2 and D2.3.

D1.3

Palette quantization is free and therefore kept

accepted

Snapping an application's colours to a named palette (a Catppuccin flavour, say) is supported as one more target of the existing capability-lowering path — not as a separate feature.

Alternatives considered
  • Drop it as an over-constraining nice-to-have.
  • Build it separately as a palette-mapping layer above the colour system.
Reasoning

Colours already stay symbolic until paint time and are lowered against a capability profile (Domain 7). “Quantize to Catppuccin” is the same operation as “quantize to 256 colours” with a different target set. It reuses the code path rather than adding one.

It was offered as droppable if constraining. It constrains nothing.

D1.4

Hot reload means whole-application dev reload, not a style watcher

accepted

A rebuild on the order of a second is acceptable for a style change. The framework does not watch style files.

Alternatives considered
  • Style-file watcher with millisecond feedback, which would have required the text format from D1.1.
  • Constrain style syntax toward literals so a template-diffing hot reload (Dioxus RSX-style) could stream style changes without recompiling.
Reasoning

Millisecond runtime responsiveness — hover, click, focus feedback — is delivered by D3.1 and has nothing to do with the dev loop. Once those two axes were separated, the dev-loop latency requirement relaxed to a normal rebuild.

Consequences

Dioxus's Subsecond hot-patching is the closest prior art. As of the material reviewed, it only tracks the tip crate — edits inside a workspace dependency are not registered, which is precisely the case when you are the framework author editing the framework. Verify against the current release before building a dev loop on it.
