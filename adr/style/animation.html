Domain 9

Animation and transitions

Designed in structurally, enabled narrowly — and one capability deliberately left out on the grounds that the cell grid makes it mostly pointless.

D9.1

The animator sits between resolution and layout

accepted

Order: merge and inherit produce target_style; the animator reads it and writes presented_style; layout and paint both read presented_style.

Alternatives considered
  • After layout — only paint properties could ever animate, which is cheaper and more predictable.
Reasoning

Placing the animator before layout costs nothing today — layout simply reads a different field — and is the only position from which an interpolated layout property could ever feed the solver. Placing it after would make layout animation structurally impossible rather than merely disabled.

D9.2

Every node carries two style slots

accepted

target_style and presented_style exist from v1, even though v1's interpolator simply copies one to the other.

Alternatives considered
  • One slot until animation ships.
Reasoning

Every write path in the framework touches the node's style slot. Adding a second slot later means revisiting all of them and deciding, at each, which one was meant. Reserving both now costs a field and a memcpy.

D9.3

v1 animates paint properties only

deferred

The Paint/Layout/Both classification gates what is animatable. Enabling layout animation later is a flag change, not a re-plumb.

Alternatives considered
  • Animate everything immediately.
  • No interpolation at all, only instant state changes.
Reasoning

An in-flight layout property means running the solver every frame for that subtree, which forfeits the event-driven layout that D3.2's dirty bits exist to provide. Paint-only keeps layout event-driven while the structure remains ready.

D9.4

Layout animation is deferred on quantization grounds

deferred

Small-delta layout animation is not worth building; large-delta panel and drawer motion remains worthwhile later.

Alternatives considered
  • Build layout tweening now for parity with web frameworks.
  • Rule it out permanently.
Reasoning

A padding easing from 0 to 4 has exactly five reachable states, so tweening it produces a five-frame stutter — and the same result is already achievable by flipping a signal and letting the existing dirty machinery relayout. The framework's tweening adds nothing at that scale.

The argument scales with magnitude, though: a sidebar sliding 0→40 cells has forty steps and reads as smooth motion. Those are the layout animations TUI users actually want, so the capability is deferred rather than rejected.

Consequences

Noted but not planned: horizontal eighth-block glyphs (▏▎▍▌▋▊▉) give eight sub-positions per cell for a moving edge, so a sliding boundary can be smoother than the grid. It works for solid fills and edges and cannot work for text.
