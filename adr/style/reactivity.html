Domain 3

Reactivity and change propagation

How a signal change reaches the screen without rebuilding the tree — and the Rust-specific ownership questions that JavaScript frameworks never have to answer.

D3.1

Node-level targeted write

accepted

A node's style may come from a reactive closure. When a dependency changes, an effect re-runs that closure only, produces a fresh Style, writes it into the node's style slot, and marks the node dirty. The component function does not re-run and the tree is not rebuilt.

Alternatives considered
  • A — React model. Re-run the component, build a new tree, diff it against the old, apply the difference.
  • C — per-property signals. Every property is its own reactive cell; only the changed one recomputes.
Reasoning

Model A re-runs user code and allocates a tree to discover that one field changed, and it puts node identity and local state at risk. Model C costs roughly 30–50 reactive graph nodes per element; at a thousand elements the graph bookkeeping exceeds the thing it optimises, because a terminal framebuffer is only 10–30k cells and is diffed cell-wise before any bytes are emitted.

In a browser, fine-grained style updates matter because touching the DOM is expensive and crosses a process boundary. Here the renderer is owned, so that asymmetry does not exist. Model B delivers the property that actually matters — a style change never re-runs the component body — for one struct write.

Consequences

Recomputing all ~40 properties of one node on every change is deliberate and cheap. The granularity of reactivity is the node, not the property.

D3.2

Two dirty bits, plus a subtree bit for inheritance

accepted

Each node carries paint_dirty and layout_dirty, set according to the changed property's Paint/Layout/Both classification. A third bit, subtree_paint_dirty, covers inherited-property changes.

Alternatives considered
  • A single dirty bit — any change triggers relayout and repaint.
  • Walk the subtree on an inherited change, marking each descendant.
Reasoning

A single bit would relayout on every colour change, which is the common case and the cheapest one. Walking the subtree on inherited changes is O(subtree) and destroys the targeted-write property from D3.1.

Paint is already a tree descent, so one bit set on an ancestor is naturally honoured by the descent — O(1) to set, no separate traversal.

Consequences

A third invalidation class exists at the global level: a terminal profile change. See D8.5.

D3.3

The node owns its style effect

accepted

Dropping a node drops the effect that writes into it.

Alternatives considered
  • Solid-style ownership tree — the effect belongs to the component's reactive owner and is disposed on unmount, holding a weak handle to the node.
Reasoning

Solid's ownership tree exists so that effects created by user code inside a component are disposed on unmount. Style effects are created by the framework at node-build time, so they are naturally node-scoped. Any arrangement where the effect can outlive its node admits stale writes into dead slots — a bug class that is miserable to trace through a reactive graph.

D3.4

Nodes live in a slotmap arena, addressed by NodeId

accepted

The effect holds a NodeId and a handle to the scheduler. Writes are index operations.

Alternatives considered
  • Rc<RefCell<Node>> tree with parent and child pointers.
Reasoning

Reactive propagation is reentrant by nature: an effect writes to a node, which marks a parent dirty, which may be mid-traversal. With RefCell that is a runtime already borrowed panic waiting to happen. An arena removes aliasing entirely and also makes the parent-pointer walks and the two-pass layered layout (D6.3) tractable.

Consequences

Retrofitting this later means rewriting every traversal in the framework. It is a foundational choice, not an optimisation.

D3.5

Merging is done explicitly in component code

accepted

A component author writes BASE.merge(theme.card()).merge(props.style). The framework provides merge and the state signals; it does not orchestrate.

Alternatives considered
  • Framework-managed merge with a registry of slot defaults and documented precedence.
Reasoning

A framework-owned merge must know slot names, default registries and precedence rules. That is a cascade, spelled in Rust — the thing D1.1 deleted.

Interactive state follows the same rule: if hovered() { s = s.merge(HOVER) } is ordinary reactive code. The framework's entire job is exposing the flag as a signal (D4.4).
